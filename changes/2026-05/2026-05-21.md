### 修复已出售订单成本价与持仓列表不一致问题

#### 问题描述
添加已出售订单时，价格成本中显示的成本价与持仓列表（按盈亏排序）中手办卡片显示的成本价不一致。

#### 问题原因
- **持仓列表成本计算**：使用 `calculate_remaining_cost_price` 方法，基于 `AssetTransaction` 库存账的 `remaining_quantity` 和 `price` 计算加权平均成本
- **添加已出售订单成本填充**：前端 `BasicInfoTab.vue` 直接使用 `figure.average_purchase_price`（手办模型的静态字段）
- 当存在卖出记录、补仓操作或多订单不同成本时，两个值会出现偏差

#### 解决方案
1. **后端新增API接口**：
   - 创建 `GET /api/sold-orders/figure-cost-price/{figure_id}/` 接口
   - 复用 `HoldingPositionService.calculate_remaining_cost_price` 方法计算实际成本
   - 同时返回当前库存数量供前端参考

2. **前端逻辑优化**：
   - 在 `useSoldOrderStore` 中添加 `fetchFigureCostPrice` 方法
   - 修改 `BasicInfoTab.vue`，选择手办后调用API获取实际成本价
   - API调用失败时使用 `average_purchase_price` 作为备选

3. **组件优化**：
   - 手办选择框添加 `loading` 状态，提升用户体验
   - 保持成本价输入框始终置灰，由系统自动填充

#### 实现逻辑
| 场景 | 成本价来源 | 计算方式 |
|------|-----------|---------|
| 持仓列表显示 | 库存账实时计算 | `Σ(price × remaining_quantity) / Σ(remaining_quantity)` |
| 添加已出售订单（修复后） | 调用后端API | 复用持仓列表相同计算逻辑 |
| API失败备选 | 手办静态字段 | `figure.average_purchase_price` |

#### 涉及文件
- `backend/app/api/sold_orders.py`: 新增获取手办成本价接口
- `frontend/src/store/index.js`: 添加 `fetchFigureCostPrice` store方法
- `frontend/src/views/SoldOrders/components/form/BasicInfoTab.vue`: 修改成本价获取逻辑

#### 结果
- 添加已出售订单时的成本价与持仓列表显示的成本价保持一致
- 成本计算基于实时库存账，反映真实的剩余持仓成本
- 提升财务数据准确性，确保盈亏计算正确

### 修复创建已出售订单 422 错误

#### 问题描述
调用 `POST /api/sold-orders/` 接口创建已出售订单时返回 422 错误，错误信息为 `shipping_date` 字段解析失败。

#### 错误信息
```json
{
    "detail": [{
        "type": "datetime_from_date_parsing",
        "loc": ["body", "shipping_date"],
        "msg": "Input should be a valid datetime or date, input is too short",
        "input": ""
    }]
}
```

#### 问题原因
- `shipping_date` 字段在 Pydantic schema 中定义为 `datetime | None = None`
- 前端提交时该字段为空字符串 `""`
- Pydantic 无法将空字符串解析为 datetime 类型，导致校验失败

#### 解决方案
在 `SoldOrderBase` 类中添加 `shipping_date` 字段的 validator：
- 在 `mode='before'` 模式下处理原始输入值
- 将空字符串、`'null'`、`'undefined'` 统一转换为 `None`
- 其他值保持原样，由 Pydantic 自动解析为 datetime

#### 实现逻辑
| 输入值 | 处理后 | 说明 |
|--------|--------|------|
| `""` (空字符串) | `None` | 未填写发货日期 |
| `"null"` | `None` | JSON null 的字符串形式 |
| `"undefined"` | `None` | JavaScript undefined 的字符串形式 |
| 有效日期字符串 | 原样保留 | Pydantic 自动解析为 datetime |

#### 涉及文件
- `backend/app/schemas/sold_order.py`: 添加 `validate_shipping_date` 字段校验器

#### 结果
- 创建已出售订单时，`shipping_date` 为空字符串不再导致 422 错误
- 未填写发货日期时正确保存为 `NULL`
- 填写了有效日期时正常解析保存

### 修复 order_transactions 卖出记录使用真实成交额

#### 问题描述
`order_transactions` 表在记录卖出订单时，使用了净额记账法（扣除运费和手续费），导致 unit_price 记录为净额（如 1938）而非真实成交额（2000）。但交易统计的"卖出总额"需要显示真实成交额。

#### 问题示例
- 卖出价：¥2,000.00
- 运费：¥50.00
- 手续费：¥12.00
- **错误记录**：unit_price = 1938（净额）
- **正确记录**：unit_price = 2000（真实成交额）

#### 问题原因
`create_sell_order_transaction` 和 `update_sold_order_transactions` 方法中，计算 unit_price 时扣除了运费和手续费：
```
unit_price = (卖出单价 × 数量 − 运费 − 手续费) / 数量
```

#### 解决方案
修改卖出记录的记账逻辑，使用真实成交额：
- `unit_price` = 卖出单价（转换为人民币）
- `total_amount` = 卖出单价 × 数量
- 运费和手续费作为独立的支出记录（fee 类型，direction=out）

#### 实现逻辑
| 字段 | 原逻辑（净额） | 新逻辑（真实成交额） |
|------|---------------|---------------------|
| unit_price | (卖出价 - 运费 - 手续费) / 数量 | 卖出价（人民币） |
| total_amount | 卖出价 × 数量 - 运费 - 手续费 | 卖出价 × 数量 |
| 运费 | 从卖出价扣除 | 独立记录（fee/out） |
| 手续费 | 从卖出价扣除 | 独立记录（fee/out） |

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_transaction_service.py`: 
  - 修改 `create_sell_order_transaction` 方法
  - 修改 `update_sold_order_transactions` 方法

#### 结果
- `order_transactions` 表正确记录真实成交额
- 交易统计的"卖出总额"显示真实成交金额
- 运费和手续费作为独立支出记录，便于财务分析

### 修复已出售订单数量修改时总价变化问题

#### 问题描述
编辑已出售订单时，如果只修改数量而不修改卖出价格，`order_transactions` 表的 `total_amount` 会自动重新计算（单价 × 新数量），导致总价改变。这不符合真实交易场景。

#### 真实交易场景
与买家谈好总价后修改数量的情况：
- 原本：数量 1，单价 700，总价 700
- 修改后：数量 2，单价 350，**总价仍为 700**

总价不应该因为修改数量而自动变化，否则账目失真。

#### 问题原因
`update_sell_transaction_quantity` 方法中，更新数量时重新计算了 `total_amount`：
```
total_amount = 卖出单价 × 新数量
```

#### 解决方案
修改 `update_sell_transaction_quantity` 方法：
- `total_amount` 保持不变（保持原总价）
- `quantity` 更新为新数量
- `unit_price` 重新计算（总价 / 新数量）

#### 实现逻辑
| 字段 | 原逻辑 | 新逻辑 |
|------|--------|--------|
| total_amount | 卖出价 × 新数量（会变） | 保持原总价（不变） |
| quantity | 新数量 | 新数量 |
| unit_price | 卖出价 | 总价 / 新数量 |

**示例**：
- 原记录：quantity=1, unit_price=700, total_amount=700
- 修改数量：new_quantity=2
- 新记录：quantity=2, unit_price=350, total_amount=700

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_transaction_service.py`: 
  - 修改 `update_sell_transaction_quantity` 方法

#### 结果
- 只修改数量时，总价保持不变
- 单价自动重新计算（总价 / 数量）
- 符合真实交易场景，避免账目失真

### 修复已出售订单数量减少时 FIFO 原则错误问题

#### 问题描述
当已出售订单的卖出数量从多改少（如从 3 个改成 1 个）时，系统错误地撤销了**最先卖出**的那部分库存，而不是按照 **FIFO（先进先出）** 原则撤销**最后卖出**的那部分。

#### 问题示例
假设订单数量变更过程：
1. 初始卖出 1 个（成本价 1300）→ 创建 sell 记录 id=10
2. 增加 2 个（成本价 600）→ 创建 sell 记录 id=11
3. 当前数量：3 个
4. 减少到 1 个：需要撤销 2 个

**错误行为**：撤销 id=10 的 1 个和 id=11 的 1 个（或只撤销 id=10）
**正确行为**：撤销 id=11 的 2 个（最后卖出的先回）

#### 问题原因
`update_quantity_on_sold_order_change` 方法中，数量减少时只查找了该订单的第一条 sell 记录（`.first()`），并使用该记录的成本价创建 RETURN 记录。当订单数量多次变更时，会创建多条 sell 记录，应该按时间倒序撤销。

#### 解决方案
修改数量减少时的处理逻辑：
1. 按 `created_at` 倒序查找该订单的所有 sell 记录
2. 从最后创建的 sell 记录开始撤销（后卖先回）
3. 计算加权平均成本价创建 RETURN 记录
4. 同步更新或软删除被撤销的 sell 记录

#### 实现逻辑
| 步骤 | 原逻辑 | 新逻辑 |
|------|--------|--------|
| 查找 sell 记录 | `.first()` 只取第一条 | `.order_by(created_at.desc()).all()` 取所有并按时间倒序 |
| 撤销顺序 | 撤销第一条（先卖出的） | 从最后一条开始撤销（后卖出的先回） |
| 成本计算 | 使用第一条的成本价 | 计算加权平均成本价 |
| sell 记录处理 | 不处理 | 全部撤销则软删除，部分撤销则更新数量 |

**FIFO 原则（后卖先回）**：
- 卖出时：按先进先出扣减库存（先买入的先卖出）
- 回库时：按后进先出恢复库存（最后卖出的先回库）

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_inventory_service.py`: 
  - 修改 `update_quantity_on_sold_order_change` 方法中的数量减少逻辑

#### 结果
- 数量减少时正确撤销最后卖出的那部分库存
- 符合 FIFO 先进先出原则
- 库存账和成本计算准确

### 修复已出售订单退款/纠纷状态库存回撤问题

#### 问题描述
当已出售订单的状态修改为"退款/纠纷"时，系统没有执行库存回撤操作。根据业务逻辑，退款/纠纷意味着交易取消，应该将已卖出的库存补回。

#### 业务场景
- 订单初始状态：已完成（卖出3个）
- 买家申请退款/发生纠纷
- 订单状态改为：退款/纠纷
- **期望**：3个库存全部回库，撤销所有卖出记录

#### 问题原因
`update_sold_order` 方法中只处理了状态字段的更新，没有针对"退款/纠纷"状态进行特殊的库存处理逻辑。

#### 解决方案
在 `update_sold_order` 方法中添加状态变更检测：
1. 检测状态是否从其他状态变为"退款/纠纷"
2. 如果是，调用库存回撤方法撤销所有卖出记录
3. 按照 FIFO 原则（后卖先回）恢复库存

#### 实现逻辑
| 步骤 | 操作 |
|------|------|
| 1 | 记录原状态，检测状态变更 |
| 2 | 如果新状态为"退款/纠纷"且原状态不是，触发库存回撤 |
| 3 | 查找该订单的所有 sell 记录（按创建时间倒序） |
| 4 | 逐个软删除 sell 记录 |
| 5 | 按 FIFO 原则恢复库存到买入记录 |
| 6 | 创建 return 记录标记回撤 |

**FIFO 原则（后卖先回）**：
- 卖出时：按先进先出扣减库存（先买入的先卖出）
- 退款时：按后进先出恢复库存（最后卖出的先回库）

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_crud_service.py`: 
  - 在 `update_sold_order` 方法中添加状态变更检测和库存回撤调用
- `backend/app/services/sold_order_service/sold_order_inventory_service.py`: 
  - 新增 `return_inventory_for_dispute` 方法处理退款/纠纷状态的库存回撤

#### 结果
- 订单状态变为"退款/纠纷"时自动执行库存回撤
- 所有卖出记录被撤销，库存完整回库
- 符合 FIFO 先进先出原则
- 库存账和交易记录保持一致

### 修复退款/纠纷状态时 order_transactions 缺少记录问题

#### 问题描述
当已出售订单状态修改为"退款/纠纷"时，`asset_transactions`（库存账）正确创建了 return 记录，但 `order_transactions`（资金账）缺少相应的退款记录，导致资金账不完整。

#### 问题原因
`return_inventory_for_dispute` 方法只处理了 `asset_transactions` 的库存回撤，没有同步处理 `order_transactions` 的资金回撤。

#### 解决方案
在 `return_inventory_for_dispute` 方法中添加对 `order_transactions` 的处理：
1. 查找该订单的所有 sell 类型 order_transactions 记录
2. 软删除这些 sell 记录
3. 创建 refund 类型的记录标记资金回撤

#### 实现逻辑
| 步骤 | 操作 | 涉及表 |
|------|------|--------|
| 1 | 查找该订单的所有 sell 类型 order_transactions | order_transactions |
| 2 | 累加退款金额，软删除 sell 记录 | order_transactions |
| 3 | 创建 refund 类型记录（direction=out） | order_transactions |

**记录类型说明**：
- `transaction_type`: refund（退款）
- `direction`: out（资金流出，退回给买家）
- `transaction_subtype`: refund（退款子类型）

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_inventory_service.py`: 
  - 修改 `return_inventory_for_dispute` 方法，添加 order_transactions 处理逻辑

#### 结果
- 退款/纠纷状态时，asset_transactions 和 order_transactions 同步记录
- 资金账完整记录退款金额
- 库存账和资金账保持一致

### 修复已出售订单从退款/纠纷恢复时未执行订单创建流程

#### 问题描述
当已出售订单的状态从"退款/纠纷"修改为"已完成"/"已发货"/"待发货"时，系统没有执行正常的订单创建流程（扣减库存、创建资金流水等）。这导致订单恢复后，库存和资金账没有相应更新。

#### 业务场景
- 订单初始状态：已完成（卖出3个）
- 发生纠纷，状态改为：退款/纠纷（库存回库）
- 纠纷解决，状态恢复为：已完成
- **期望**：重新扣减库存，创建资金流水

#### 解决方案
在 `update_sold_order` 方法中添加状态变更检测：
1. 检测状态是否从"退款/纠纷"变为"已完成"/"已发货"/"待发货"
2. 如果是，执行正常的订单创建流程：
   - 创建卖出订单主记录和资金流水
   - 扣减库存数量
   - 更新手办聚合状态

#### 实现逻辑
| 步骤 | 操作 |
|------|------|
| 1 | 记录原状态，检测状态变更 |
| 2 | 如果原状态为"退款/纠纷"且新状态为正常状态，触发订单创建流程 |
| 3 | 创建尾款管理记录和资金流水 |
| 4 | 扣减库存数量 |
| 5 | 更新手办聚合状态 |

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_crud_service.py`:
  - 在 `update_sold_order` 方法中添加状态变更检测和订单创建流程

#### 结果
- 订单从退款/纠纷状态恢复时，自动执行正常的订单创建流程
- 库存正确扣减，资金流水正确创建
- 库存账和资金账保持一致
