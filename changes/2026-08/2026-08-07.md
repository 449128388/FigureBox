## 缺陷修复 → 2. 资产看板-持仓列表「查询全部数据」只显示 9 条（实际 32 条）且缺少翻页功能

**解决方案：** 资产看板-持仓列表（按盈亏排序）点击「查询」按钮（无条件查询全部数据）时，前端调用 `GET /api/assets/holdings/filter?page=1&page_size=9`。后端 [operation_holding_filter.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/api/dashboard/assets/operation_holding_filter.py) 的 `filter_holdings` 正确地做了**服务端分页**，返回 `{holdings: 当前页9条, total: 32, page: 1, page_size: 9, total_pages: 4, filter_options}` —— 后端逻辑本身没问题（32 条数据按每页 9 条分成 4 页）。缺陷在前端 [HoldingsList.vue](file:///e:/项目编写/项目编写/FigureBox/frontend/src/views/Dashboard/components/reseller/assets/HoldingsList.vue) 的 `handleSearch`：它只把响应里的 `data.holdings`（**仅当前页 9 条**）存进 `filteredHoldingsData`，却**完全忽略了 `data.total`（32）**。而 [useHoldingsPagination.js](file:///e:/项目编写/项目编写/FigureBox/frontend/src/views/Dashboard/composables/useHoldingsPagination.js) 的 `total` computed 又是用 `dataSource.length`（即 `filteredHoldingsData.length`）计算 —— 于是 `total` 显示为 9，`total_pages` 被算成 1 页，翻页器只有 1 页且无下一页，**剩下的 23 条永远无法看到**。修法分三层：① 给 `useHoldingsPagination` 增加可选参数 `totalOverride`（外部总条数 ref），传入后 `total` 优先取外部值、`paginatedData` 直接返回数据源（服务端分页模式下数据源本身已是当前页，不再二次切片）；② `HoldingsList` 新增 `serverTotal` ref，`handleSearch` 成功后把后端 `data.total` 存入，并通过 `totalOverride` computed（仅搜索态生效）传给 composable，翻页器按 32 条展示 4 页；③ 翻页器触发 `handlePageChange` / `handleSizeChange` 时，若处于搜索态则**重新携带 page / page_size 请求后端**，取回对应页数据（服务端分页，翻页真正落地）；非搜索态（未点过查询）仍走原来的客户端切片分页，行为不变。

**实现逻辑：**

- **composable 支持外部 total（`useHoldingsPagination(dataSource, totalOverride = null)`）**：

  - `paginatedData` computed：`totalOverride.value` 是 number 时直接返回 `dataSource`（服务端已按当前页返回数据，若再按 page 切片会切空）；否则保留原客户端 `slice(start, end)` 逻辑

## 缺陷修复 → 3. 资产看板-持仓列表（按盈亏排序）点击分页没有对应接口响应

**解决方案：** 上一版（#2）修复了「查询全部数据只显示 9 条、缺翻页」的问题，但引入了一个残留缺陷：`handlePageChange` / `handleSizeChange` 中包裹了 `if (hasSearched.value)` 守卫 —— **只有点击过「查询」按钮进入搜索态后，翻页才会请求后端接口**；而用户**未点击查询**、直接进入资产看板看默认持仓列表时，翻页只是对 `dashboardData.holdings`（首屏 `/assets/dashboard/holdings` 拉回的全量 32 条内存数组）做纯客户端 `slice`，Network 面板中**看不到任何 `GET /api/assets/holdings/filter?page=X&page_size=Y` 请求**。这与用户对「手办库 / 尾款管理」模块「翻页必须走接口」的既有认知不一致。修法：把 `handlePageChange` / `handleSizeChange` 中的 `if (hasSearched.value)` 守卫**删除**，让翻页/每页条数变化**无条件触发 `handleSearch()`** —— 即任何分页操作都携带当前 `page` / `page_size`（以及已填写的 keyword / status）请求 `/assets/holdings/filter`，翻页真正由后端响应驱动。首次翻页后 `handleSearch` 内部会把 `hasSearched` 置为 true、`serverTotal` 记录后端 total，数据源无缝切换到服务端分页模式（沿用 #2 的 `totalOverride` / `paginatedData` 机制），后端返回的正是当前页数据。未搜索态点击分页时，由于 `handleSearch` 携带的 keyword / status 为空，后端等价于「查询全部数据」，返回结果与首屏 `dashboardData.holdings` 数据集合一致，0 视觉跳变。

- **数据一致性保障**：默认态（无 keyword / status）请求 `filter` 接口等价于「查询全部数据」，后端返回集合与首屏 `dashboardData.holdings` 一致，首次翻页后视图 0 跳变；`page` / `page_size` 用 `handleSearch` 内部当前 ref 值构造 params，与 el-pagination 的 `v-model:current-page` / `v-model:page-size` 双向绑定时序兼容

  - 搜索态翻页链路（#2）0 影响（行为不变，只是守卫条件恒真，等价于删除）
  - 重置按钮链路（清空搜索态 + 回第 1 页 + 恢复 dashboard 全量数据）0 影响

## 重构 → 6. 许可数据从 users_info 表剥离到独立 user_licenses 表（1:1 FK 关联）

**解决方案：** 上一版（#5）虽然把 10 个 license_* 列通过 SQLAlchemy Mixin 模式剥离到独立文件 [license.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/models/license.py) 的 LicenseMixin，**但物理表结构上仍合并在 `users_info` 里** —— 这只是「代码组织上的分离」而非「数据架构上的分离」。`users_info` 已被 MinIO / Email / Backup / Timeout / Push / Privacy / 头像 / 个人资料 / 偏好设置 / 各种时间戳 等 Feature 字段占据 **90+ 列**，许可字段继续挂在 `users_info` 上会让这张主表继续膨胀（**每加一个 Feature 字段都要 ALTER users_info**，与 SQLAlchemy 声明式 schema 管理冲突；历史表 / 多用户共享许可 / 独立备份 / 跨用户许可审计 等高级能力也无从下手）。修法：把 10 个 `license_*` 列从 `users_info` **物理剥离**到新建的独立表 `user_licenses`，通过 `user_id` 外键 + UNIQUE 约束实现 1:1 关联（一个用户最多一条许可记录），User 模型新增 `User.license` relationship（`lazy="selectin"` 自动走单独 SELECT 加载，0 N+1），业务层从「`user.license_key = ...`」改为「`user.license.license_key = ...`」（通过新增的 `_ensure_license()` helper 处理老用户 `user.license is None` 场景，自动创建空记录）。这样 `users_info` 重新瘦身（移除 10 列），许可数据可独立备份 / 历史可平滑扩展到 license_history 表 / 多端共享许可等 P1 高级能力成为可能。数据库 schema 0 业务字段变化（10 列完全等价搬移），前端 0 改动（API 端点 / 响应字段 0 变化），`license_service.py` 业务逻辑 0 变化（仅是访问路径从 `user.x` → `user.license.x`）。4 步幂等迁移脚本 [migrate_license_to_separate_table_20260807.py](file:///e:/项目编写/项目编写/FigureBox/backend/migrations/migrate_license_to_separate_table_20260807.py)：① 校验 v2 列存在 → ② INSERT IGNORE 数据迁移（重跑幂等）→ ③ CREATE TABLE user_licenses + UNIQUE + 复合索引 + FK CASCADE → ④ ALTER TABLE users_info DROP 10 列；已执行完毕，新表 0 行（无历史数据）+ 旧列 0 残留。
