## 缺陷修复 → 2. 首页「最近动态」`/api/home/activities` 缺少数据隔离

**解决方案：** 用户登录首页看到的「最近动态」中，「价格变动」类目会把**全站所有用户**的手办价格变更记录都拉出来——A 用户在首页能看到 B 用户手办的价格变动事件，跨用户隐私泄漏。根因是 [home_service.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/home_service/home_service.py) `get_activities` 4 个子查询中前 3 个（订单 / 卖出 / 愿望）已正确带 `user_id` 过滤，但第 4 段「价格变动」直接 `db.query(AssetPriceHistory).order_by(date.desc())` 无任何 user 维度过滤；同时 [AssetPriceHistory](file:///e:/项目编写/项目编写/FigureBox/backend/app/models/asset_transaction.py) 表本身**未建 `user_id` 字段**（仅通过 `figure_id` 间接关联手办），需要在查询时 JOIN `figures` 表再按 `Figure.user_id` 二次过滤。修法：在价格变动查询中加 JOIN + `Figure.user_id == user_id` + `Figure.is_active == 1` 过滤，并在循环内补一道 `Figure.user_id` 二次校验作为防御性兜底，防止未来数据迁移时出现孤儿价格记录。

**实现逻辑：**

- **【#2 阶段 1】[home_service.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/home_service/home_service.py) `get_activities` 第 4 段 JOIN Figure 过滤**：`db.query(AssetPriceHistory).join(Figure, Figure.id == AssetPriceHistory.figure_id).filter(Figure.user_id == user_id, Figure.is_active == 1)` —— 通过 figure_id 关联到手办表后按当前用户过滤，未软删除 / 非当前用户的手办价格记录全部排除
- **【#2 阶段 2】循环内 figure 二次校验**：在遍历 `price_records` 拼装活动时，`db.query(Figure).filter(Figure.id == pr.figure_id, Figure.user_id == user_id).first()` —— 即便 JOIN 因 LEFT JOIN 行为差异或历史脏数据出现极小概率泄漏，二次过滤也能兜住，仅返回当前用户可见的活动
- **【#2 阶段 3】与前 3 段子查询的隔离架构保持一致**：订单 / 卖出 / 愿望 3 段在 #19 改造中已加 `user_id` 过滤，本次仅补齐第 4 段，4 段子查询现在全部走「按 user 隔离」的统一模型
- **不变量**：
  - 0 前端改动（首页组件仍调 `GET /api/home/activities`，响应结构 0 改动）
  - 0 数据库结构变更（`asset_price_history` 表 0 改动，未新增 user_id 列）

## 缺陷修复 → 3. 尾款管理（订单管理）搜索按钮点击后缺少后端查询接口

**解决方案：** 用户在尾款管理页面（`/orders`）输入「手办名称 / 出荷日期范围」条件后点击「搜索」按钮，列表**不会**按条件过滤——按钮仅做「重置到第 1 页」的本地动作，过滤完全依赖前端 `searchFilteredOrders` 计算属性对 `orderStore.orders` 缓存数组的内存过滤（只在用户输入时被动响应）。根因是 [useOrderManagement.js](file:///e:/项目编写/项目编写/FigureBox/frontend/src/views/Orders/composables/useOrderManagement.js) `handleSearch` 只重置页码、从后端拉取的入口 `orderStore.fetchOrders`（[store/index.js:200](file:///e:/项目编写/项目编写/FigureBox/frontend/src/store/index.js#L200)）只发 `axios.get('/orders/')` 不带任何参数；而 [orders.py:30-64](file:///e:/项目编写/项目编写/FigureBox/backend/app/api/orders.py#L30-L64) `GET /orders/` 早**已支持** `figure_name / due_date_start / due_date_end` 三个查询参数（由 [order_query_service.py:57-110](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/order_service/order_query_service.py#L57-L110) 实现完整过滤逻辑），但前端从未透传，导致「搜索按钮按下后端 0 数据库查询」——大量历史订单时也只看前端缓存的当前页数据，跨页 / 跨会话的搜索结果会失真。修法：① store 的 `fetchOrders` 接受 `params` 入参并通过 axios `params` 字段透传；② composable 的 `handleSearch` 把当前搜索框状态组装成 `{figure_name, due_date_start, due_date_end}` 后调用 `fetchOrders(params)`；③ `handleReset` 清空搜索条件后调用 `fetchOrders()` 重新拉取全量数据。

**实现逻辑：**

- **【#3 阶段 1】[store/index.js](file:///e:/项目编写/项目编写/FigureBox/frontend/src/store/index.js) `fetchOrders` 接受 `params` 入参并透传**：`async fetchOrders(params = {})` → `axios.get('/orders/', { params })`，向后端查询参数透传；不传时 `params = {}` → 走全量拉取，向后兼容所有已有调用方（`createOrder` / `updateOrder` / `deleteOrder` 等 0 改动）
- **【#3 阶段 2】[useOrderManagement.js](file:///e:/项目编写/项目编写/FigureBox/frontend/src/views/Orders/composables/useOrderManagement.js) `handleSearch` 真实触发后端查询**：

  - 把 `searchDueDateRange.value[0] / [1]` 赋值给 `params.due_date_start / due_date_end`（长度 = 2 时）
  - `await orderStore.fetchOrders(params)` —— 让 [orders.py:30-64](file:///e:/项目编写/项目编写/FigureBox/backend/app/api/orders.py#L30-L64) 真正按条件 SQL 查询
