## 缺陷修复 → 2. 首页「最近动态」`/api/home/activities` 缺少数据隔离

**解决方案：** 用户登录首页看到的「最近动态」中，「价格变动」类目会把**全站所有用户**的手办价格变更记录都拉出来——A 用户在首页能看到 B 用户手办的价格变动事件，跨用户隐私泄漏。根因是 [home_service.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/home_service/home_service.py) `get_activities` 4 个子查询中前 3 个（订单 / 卖出 / 愿望）已正确带 `user_id` 过滤，但第 4 段「价格变动」直接 `db.query(AssetPriceHistory).order_by(date.desc())` 无任何 user 维度过滤；同时 [AssetPriceHistory](file:///e:/项目编写/项目编写/FigureBox/backend/app/models/asset_transaction.py) 表本身**未建 `user_id` 字段**（仅通过 `figure_id` 间接关联手办），需要在查询时 JOIN `figures` 表再按 `Figure.user_id` 二次过滤。修法：在价格变动查询中加 JOIN + `Figure.user_id == user_id` + `Figure.is_active == 1` 过滤，并在循环内补一道 `Figure.user_id` 二次校验作为防御性兜底，防止未来数据迁移时出现孤儿价格记录。

**实现逻辑：**

- **【#2 阶段 1】[home_service.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/home_service/home_service.py) `get_activities` 第 4 段 JOIN Figure 过滤**：`db.query(AssetPriceHistory).join(Figure, Figure.id == AssetPriceHistory.figure_id).filter(Figure.user_id == user_id, Figure.is_active == 1)` —— 通过 figure_id 关联到手办表后按当前用户过滤，未软删除 / 非当前用户的手办价格记录全部排除

- **【#2 阶段 3】与前 3 段子查询的隔离架构保持一致**：订单 / 卖出 / 愿望 3 段在 #19 改造中已加 `user_id` 过滤，本次仅补齐第 4 段，4 段子查询现在全部走「按 user 隔离」的统一模型

## 缺陷修复 → 4. 手办库-手办详情页多出 2 个冗余接口

## 缺陷修复 → 14. 尾款管理 `/orders/?status=未支付` 接口 500 错误（NULLS LAST 语法在 MySQL 不支持）

**解决方案：** 上一版给 `/orders/` 端点加分页时，[order_query_service.py](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/order_service/order_query_service.py) `get_orders_page` 用了 `.order_by(Order.due_date.asc().nullslast(), Order.id.desc())` 想实现「NULL 排最后 + due_date 升序」语义。SQLAlchemy 的 `.nullslast()` 在 MySQL 方言下**不重写 SQL**，直接生成原生 `ORDER BY ... ASC NULLS LAST`，而 `NULLS FIRST` / `NULLS LAST` 是 PostgreSQL 8.3+ 扩展语法，MySQL 8.0.45 不支持，导致带 status 参数的请求 `GET /orders/?status=未支付&skip=0&limit=10` 直接报 `pymysql.err.ProgrammingError: (1064, "...right syntax to use near 'NULLS LAST, orders.id DESC ...'")` 返回 500。修法：① 把 `Order.due_date.asc().nullslast()` 替换为 MySQL 兼容写法 `Order.due_date.is_(None), Order.due_date.asc()`；② 排序语义等价：`is_(None)` 生成 `IS NULL` 表达式，NULL 返 1、非 NULL 返 0，升序排序时 NULL（1）排在非 NULL（0）之后，正好等价于「NULL 排最后」；③ `id DESC` tie-breaker 保留；④ 同时检查 `get_orders` 无 `order_by`（未触发该问题），0 改动。

**实现逻辑：**

- **MySQL 兼容性替换**：
  ```python
  # 修复前（生成 ASC NULLS LAST 语法，MySQL 8.0 不支持）
  orders = paged_query.order_by(
      Order.due_date.asc().nullslast(),
      Order.id.desc()
  ).offset(skip).limit(limit).all()

  # 修复后（MySQL 兼容写法，语义等价）
  orders = paged_query.order_by(
      Order.due_date.is_(None),  # NULL=1, 非 NULL=0, 升序时 NULL 排最后
      Order.due_date.asc(),       # 非 NULL 按 due_date 升序
      Order.id.desc()             # tie-breaker
  ).offset(skip).limit(limit).all()
  ```
- **生成的 SQL 对比**：
  - 修复前：`ORDER BY orders.due_date ASC NULLS LAST, orders.id DESC LIMIT 0, 10`（MySQL 8.0.45 解析失败，1064 语法错误）
  - 修复后：`ORDER BY orders.due_date IS NULL, orders.due_date ASC, orders.id DESC LIMIT 0, 10`（MySQL 标准语法，正确执行）

  - `due_date` 为 NULL 的订单 → `IS NULL` 表达式返 1，asc 排序时排在最后

**解决方案：** 已出订单页面 [useSoldOrderManagement.js](file:///e:/项目编写/项目编写/FigureBox/frontend/src/views/SoldOrders/composables/useSoldOrderManagement.js) 中存在一个客户端 `searchFilteredOrders` computed —— 用户在「手办名称 / 订单编号 / 卖出平台」3 个搜索输入框中**键入字符的瞬间**，computed 自动重算、按 `figure_name.toLowerCase().includes(keyword)` / `order_number.toLowerCase().includes(keyword)` / `sell_platform ===` 3 个规则在前端对 `soldOrderStore.soldOrders` 内存数组做实时过滤；`filteredOrders`（叠加状态 Tab 过滤+排序）、`statusCounts`（状态计数）、`totalNetProfit`（累计净利润）3 个下游 computed 都直接依赖 `searchFilteredOrders.value`，导致用户每敲一个字符就触发一次 Vue 响应式重算。这与上一版（#15）建立的「搜索仅在点击按钮/按 Enter 时通过后端接口生效」语义冲突 —— 用户尚未点击搜索就看到了过滤后的列表，搜索按钮失去了"主动查询"的语义、误以为后端已经按输入实时返回结果（实际只是前端内存过滤、跨页/分页场景下结果会失真）。修法：① 删除整个 `searchFilteredOrders` computed；② `filteredOrders` 改为直接消费 `soldOrderStore.soldOrders`（store 中已是后端最近一次按搜索条件过滤后的结果）+ 仅叠加 `currentStatus` 状态 Tab 过滤（状态 Tab 是另一种 UI 控件，与「搜索」概念分离，保留本地切换语义合理）；③ `statusCounts` 改为直接基于 `soldOrderStore.soldOrders` 聚合（搜索后 store 中的数据已含搜索过滤结果，状态计数自然反映当前搜索视图）；④ `totalNetProfit` 同样改为直接 reduce `soldOrderStore.soldOrders`；⑤ 搜索框 v-model 仍双向绑定到 `searchFigureName` / `searchOrderNumber` / `searchSellPlatform`（用于点击搜索时构造 params），仅其「键入即过滤」的副作用被切断。
