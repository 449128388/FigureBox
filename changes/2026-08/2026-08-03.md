## 缺陷修复 → 2. 自动备份调度器首次执行抛 `offset-naive vs offset-aware` 异常

**解决方案：** 部署后第一次启动调度器立即执行扫描，「扫描到 1 个启用用户」后立即抛 `TypeError: can't subtract offset-naive and offset-aware datetimes`，根因是 MySQL DATETIME 字段没有时区信息，SQLAlchemy 从 DB 读出的 `user.last_auto_backup_at` 是 naive datetime，但调度器逻辑里 `datetime.now(BEIJING_TZ)` 是 aware datetime，两者直接相减触发异常；异常隔离机制生效（log error 后继续，单用户失败不影响其他用户）。本次在 `_should_run` 相减前加一道 naive→aware 兜底（`last_at.tzinfo is None` 时 `BEIJING_TZ.localize(last_at)`），DB 写时仍用 `datetime.now(BEIJING_TZ)` 保持 aware 不变。

**实现逻辑：**

- **唯一变更** [auto_backup_scheduler.py:131-136](file:///e:/项目编写/项目编写/FigureBox/backend/app/services/scheduler_service/auto_backup_scheduler.py#L131-L136) `_should_run`：
  - 取出 `user.last_auto_backup_at` 后做 `tzinfo` 判断
  - 若为 None（naive datetime）→ `BEIJING_TZ.localize(last_at)` 显式标注北京时间
  - 再用 `datetime.now(BEIJING_TZ) - last_at` 相减 → 永远 aware-aware，零异常
- **保持不变**：
  - DB 写时 `user.last_auto_backup_at = datetime.now(BEIJING_TZ)` 不动（仍为 aware）
  - 异常隔离机制（`try/except` 单用户失败 log error 继续）保持
  - 调度频率、到期判定逻辑、FREQUENCY_SECONDS 字典均不变
  - `_run_for_user` 内部不访问 `last_auto_backup_at`（只写），不受影响
- **修复链路**：`AutoBackupScheduler._check_and_run` → 遍历用户 → `_should_run(user)` → `datetime.now(BEIJING_TZ) - user.last_auto_backup_at` → 触发 TypeError → 异常被 `_check_and_run` 捕获 log error → 下个用户继续
- **根因说明**：MySQL `DATETIME` 类型本身不存时区（`TIMESTAMP` 才是 UTC），SQLAlchemy 反射为 `DateTime`（naive），与 Python 业务代码普遍用 `datetime.now(BEIJING_TZ)` 形成的 aware datetime 形成不一致。修复采用「读时按需打时区」而非「写时强转 naive」—— 后者会丢失时区语义，未来若加时区感知能力（如多区域用户）需返工
- **数据零变动 / 业务零回归**：纯相减逻辑补丁，未改写任何业务表数据，未影响已写记录的合法性
- **影响接口**：`/openapi.json` 端点列表无变化；调度器启动后立即执行扫描：1 个启用用户 → 成功 1 / 跳过 0 / 失败 0 → last_auto_backup_at 写入 2026-08-03 16:43:38 + 1 条 type=auto 记录自动生成 + 宿主机 `backups_data/1/figurebox_backup_2026-08-03_16-43-38.json` 落盘
- **影响场景**：
  - 用户开启自动备份（首次 / 频率 daily 距上次 >24h / weekly 距上次 >7d / monthly 距上次 >30d）→ 调度器正常执行
  - DB 老数据（naive datetime）→ 兼容运行
  - DB 新数据（aware datetime）→ 同样兼容（`tzinfo is not None` 走 else 分支）
