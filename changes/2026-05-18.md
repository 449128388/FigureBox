## 修复资产看板-盈亏分析取值问题

### 问题描述
资产看板-盈亏分析中的浮动盈亏、实现盈亏、总收益率取值不正确，使用了错误的计算逻辑和模拟数据。

### 解决方案
创建独立的盈亏分析服务 `ProfitAnalysisService`，实现正确的盈亏计算逻辑。

### 实现逻辑
1. **浮动盈亏计算**：
   - **含义**：当前还在手里的手办，如果今天按市场价全部卖掉，理论上能赚多少钱
   - **公式**：浮动盈亏 = Σ[(手办当前市场价 − 加权平均成本价) × 剩余库存数量]
   - **数据来源**：`AssetTransaction` 表的 `remaining_quantity` 和 `price` 字段

2. **实现盈亏计算**：
   - **含义**：已经卖出去的手办，扣除成本、运费、手续费后，真正到手的净利润
   - **公式**：实现盈亏 = 已出售订单中累计净利润
   - **数据来源**：`SoldOrder.net_profit` 字段

3. **总收益率计算**：
   - **含义**：从投资手办至今，整体资金回报率
   - **公式**：总收益率 = (浮动盈亏 + 实现盈亏) / 总投入成本 × 100%
   - **保留位数**：小数点后2位

4. **本月入手数量**：
   - **原问题**：使用模拟数据 `monthly_purchases = 3`
   - **修复**：使用真实统计，查询本月创建的订单数量

5. **前端组件优化**：
   - 删除模拟数据默认值
   - 添加根据盈亏正负自动切换颜色的逻辑
   - 盈利显示红色，亏损显示绿色（中国股市标准）

- **结果**：盈亏分析数据准确反映实际投资情况

## 新增塑料手办指数涨跌功能

### 需求描述
资产看板中的塑料手办指数需要显示涨跌情况，反映用户持仓手办的整体市值变化。

### 解决方案
创建塑料手办指数服务 `PlasticIndexService`，实现指数的涨跌计算和历史记录管理。

### 实现逻辑
1. **指数涨跌核心逻辑**：
   - 持仓手办市场价上涨（闲鱼成交价↑）→ 指数涨（成分股市值增加）
   - 持仓手办市场价下跌（破发、再版）→ 指数跌（成分股市值缩水）
   - 买入高价/热门手办 → 指数涨（通常）（新增高市值成分股）
   - 卖出低价/亏损手办 → 指数涨（可能）（剔除低市值成分股，指数提纯）
   - 卖出高价/盈利手办 → 指数跌（可能）（优质成分股被剔除）
   - 手办再版/大量出货 → 指数跌（市场供给增加，价格崩盘）

2. **指数计算公式**：
   - 塑料指数 = 基准日指数 × (当前总市值 / 基准日总市值)
   - 基准日 = 最早购买手办的日期（开户首日）
   - 基准日总市值 = 基准日当天所有持仓手办的平均入手价格总和

3. **涨跌计算**：
   - 与昨日指数记录对比计算涨跌额和涨跌幅
   - 无昨日记录时与基准日指数（1000）对比
   - 涨跌趋势：涨/跌/平

4. **数据存储**：
   - 创建 `plastic_index_history` 表记录每日指数
   - 字段：用户ID、当前指数值、涨跌值、涨跌幅、基准值、基准日期、记录日期

5. **前端展示**：
   - 塑料手办指数显示当前值和涨跌幅
   - 涨显示红色▲，跌显示绿色▼，平显示灰色-
   - 与上证指数、沪深300展示风格保持一致

- **结果**：塑料手办指数能够实时反映持仓市值变化，支持涨跌趋势分析

## 修复最大回撤仍为+0.00%问题

### 问题描述
上一轮修复使用 AssetValueCache 计算最大回撤，但由于缓存存储的总资产公式与用户定义不一致，最大回撤仍然显示 +0.00%。

### 解决方案
移除对 AssetValueCache 的依赖，直接使用总投入成本作为历史峰值参考。

### 实现逻辑
- **问题原因**：AssetValueCache 由 `TotalAssetsCalculator.calculate_by_orders()` 填充，其公式为 `Σ(手办市场价 × 剩余数量)`（仅统计持仓市值约 ¥6,870）。而用户定义的 `总资产 = 总投入成本 + 实现盈亏 + 浮动盈亏`（约 ¥11,356）。两者公式不匹配，导致缓存值始终低于当前总资产，`MAX(缓存, 当前) = 当前`，回撤恒为 0%
- **修复方法**：移除缓存查询，直接使用 `总投入成本` 作为最保守的历史峰值估计。`历史峰值 = MAX(当前总资产, 总投入成本)`。当用户盈利时（当前 > 投入），峰值=当前，回撤=0%（处于或接近历史高点）
- **数据验证**：已完成订单总投入=¥6,900，当前总资产=¥11,356，峰值=¥11,356，回撤=(11356-11356)/11356=0%

- **结果**：最大回撤使用统一的总资产定义，计算逻辑清晰

## 修复 Dashboard API 500 错误（MySQL sort buffer 溢出）

### 问题描述
修改为使用入手日期后，Dashboard API 报错 500，错误信息为 `Out of sort memory, consider increasing server sort buffer size`。

### 解决方案
将 `ORDER BY ... LIMIT 1` 的排序查询改为 `MIN()` 聚合函数直接取最小值，彻底避免排序操作。

### 实现逻辑
- **问题原因**：`WHERE id IN (子查询) ORDER BY purchase_date ASC LIMIT 1` 虽然避免了 JOIN，但 `IN (子查询)` 返回的 Figure ID 数量仍然很大，MySQL 需要对大量行按 `purchase_date` 排序，超出默认 sort buffer 大小
- **修复方法**：使用 `SELECT MIN(purchase_date)` 聚合查询替代 `ORDER BY purchase_date ASC LIMIT 1`。`MIN()` 通过逐行扫描直接得出最小值，不需要 sort buffer
- **SQL 对比**：
  - ❌ 旧 SQL：`SELECT * FROM figures WHERE id IN (...) AND purchase_date IS NOT NULL ORDER BY purchase_date ASC LIMIT 1`（需要排序）
  - ✅ 新 SQL：`SELECT MIN(purchase_date) FROM figures WHERE id IN (...) AND purchase_date IS NOT NULL`（无需排序）

- **结果**：Dashboard API 正常返回数据

## 实现塑料小人指数(HPI)

### 需求描述
行情页需要展示塑料小人指数(HPI)，与资产看板的塑料手办指数有本质区别：
- **塑料手办指数**：仅持仓手办，个人大盘
- **塑料小人指数HPI**：全市场手办，行业大盘（类比上证指数）

### 核心差异
| 指标 | 样本范围 | 定位 | 类比股市 |
|------|----------|------|----------|
| 塑料手办指数 | 仅持仓手办 | 个人大盘 | 个股自选股组合 |
| 塑料小人指数HPI | 全市场手办 | 行业大盘 | 上证指数、沪深300 |

### 涨跌定义
- **涨**：今日HPI > 昨日HPI，市场升温
- **跌**：今日HPI < 昨日HPI，市场降温
- **平**：|今日HPI - 昨日HPI| < 0.1%，市场横盘

### 解决方案
创建独立的HPI服务层，基于全市场手办数据计算综合价格指数。

### 实现逻辑
- **服务层创建**：`app/services/dashboard_service/market_service/hpi_service.py`
  - `HPIService.calculate_hpi()`：计算HPI指数、涨跌、趋势
  - `HPIService.get_sector_performance()`：获取板块涨幅排行
  - `HPIService.get_watchlist()`：获取热门手办列表
  - `HPIService.get_research_report()`：获取智能投研报告
- **业务层调整**：`market/dashboard.py`
  - 移除原有的持仓手办相关逻辑
  - 统一调用HPI服务层获取全市场数据
- **架构优化**：行情看板完全基于全市场数据，与资产看板的个人持仓数据分离

- **结果**：行情看板展示市场级HPI指标，与资产看板的个人指数形成互补

## HPI指数优化（成交量加权法）

### 问题描述
原HPI计算采用简单市值平均法，无法反映交易活跃度对指数的影响，不符合专业指数编制标准。

### 解决方案
采用成交量加权法计算HPI，实现成分股动态管理，建立与其他模块的互动关系。

### 实现逻辑
- **指数计算优化**：
  - 计算公式：HPI = Σ(手办市场价 × 成交量) / 总成交量
  - 高价且交易活跃的手办对指数影响更大，符合"大盘"概念
- **成分股管理**：
  - 纳入：有成交量的活跃手办
  - 剔除：90天无交易的"僵尸股"
  - 权重：按成交量动态加权
- **模块互动关系**：
  - HPI → 资产看板：提供"大盘基准"用于"跑赢大盘"计算
  - 资产看板 → HPI：持仓交易数据贡献到成交量统计
  - HPI → 持仓卡片：提供涨跌状态判定标准
  - 交易 → HPI：卖出成交计入成交量
  - HPI → 交易决策：市场冷热信号指导买卖
  - HPI → 预警：单日跌幅>5%触发系统性风险预警
- **新增功能**：
  - `get_hpi_for_asset_comparison()`：供资产看板对比使用
  - `check_systemic_risk()`：系统性风险检查（跌幅>5%触发预警）

- **结果**：HPI成为手办界的"上证指数"，与资产看板、持仓卡片、交易模块、预警模块形成闭环

资产看板-交易模块的卖出统计需要按新需求调整统计逻辑，明确统计范围和口径。

### 解决方案
调整卖出统计的查询数据源和筛选条件，从 `SoldOrder` 表改为 `order_transactions` 表，按 `transaction_type` 筛选。

### 实现逻辑
- **统计范围调整**：
  - 统计本月内所有资金流入的卖出行为
  - 包含：库存手办卖出成交
  - 不包含：仅挂出未成交、订单取消
- **数据源调整**：
  - 从 `order_transactions` 表中筛选（原为 `SoldOrder` 表）
  - 条件改为 `transaction_type = 'SELL'` 且 `transaction_date` 在本月内
  - 原条件 `SoldOrder.status == "已完成"` 改为 `OrderTransaction.transaction_type == "SELL"`

- **结果**：卖出统计逻辑符合业务需求，数据口径清晰明确

## 资产看板-交易模块净现金流逻辑优化

### 问题描述
资产看板-交易模块的净现金流需要按新需求调整计算公式和展示方式。

### 解决方案
调整净现金流计算公式，修改前端展示逻辑，实现正确的颜色标识。

### 实现逻辑
- **公式调整**：
  - 新公式：`净现金流 = 买入总额 - 卖出总额`
  - 原公式：`净现金流 = 卖出总额 - 买入总额`
- **方向判定**：
  - `> 0` 表示净流出，显示 `(支出>收入)`，表示本月净投入
  - `< 0` 表示净流入，显示 `(收入>支出)`，表示本月净回笼
- **颜色标识**：
  - 净流入（收入>支出）：标红 🔴
  - 净流出（支出>收入）：标绿 🟢

- **结果**：净现金流展示符合业务需求，数据含义清晰明确

## 资产看板-交易模块月份切换功能

### 问题描述
资产看板-交易模块需要支持查看历史月份数据，并明确时间边界和边界情况处理规则。

### 解决方案
新增月份切换器组件，修改后端API支持按指定年月查询，明确自然月时间边界和边界情况处理规则。

### 实现逻辑
- **月份切换器组件**：
  - 创建 `MonthSelector.vue` 组件，支持左右箭头切换月份
  - 显示格式如 `< 2026年5月 >`
  - 限制范围：2020年1月至当前月份
- **后端API改造**：
  - `trade_records.py` 接口新增 `year` 和 `month` 查询参数
  - 使用自然月模式：当月1日 00:00:00 至 当月最后一日 23:59:59
  - 使用 `monthrange` 计算月份最后一天
- **前端数据流**：
  - `Dashboard.vue` 管理当前选中月份状态
  - 月份切换时触发重新加载交易数据
  - `TradeView.vue` 接收月份参数并传递给子组件
- **时间边界处理**：
  - 自然月模式：与账单周期对齐，最常用
  - 跨月订单：按实际付款时间拆分统计
  - 退款/退货：生成反向流水从当月统计中扣减

- **结果**：支持查看历史月份交易数据，时间边界清晰，边界情况处理规范

## 资产看板-交易模块边界情况处理优化

### 问题描述
资产看板-交易模块需要完善边界情况处理逻辑，包括跨月订单拆分统计、退款扣减、退货扣减等场景。

### 解决方案
修改月度统计服务，支持按实际付款时间拆分统计，通过反向流水处理退款和退货。

### 实现逻辑
- **跨月订单处理**：
  - 按实际付款时间拆分统计
  - 上月定金计入上月买入，本月尾款计入本月买入
  - 通过 `transaction_date` 字段精确到每笔付款时间
- **退款处理**：
  - 生成反向流水（`transaction_type = 'REFUND'`）
  - 从当月买入金额中扣减退款金额
  - 买入笔数仅统计正向交易，退款不计入笔数
- **退货处理**：
  - 生成反向流水（`transaction_type = 'RETURN'`）
  - 从当月卖出金额中扣减退货金额
  - 卖出笔数仅统计正向交易，退货不计入笔数
- **金额计算逻辑**：
  - 买入金额 = BUY类型金额总和 - REFUND类型金额总和
  - 卖出金额 = SELL类型金额总和 - RETURN类型金额总和

- **结果**：边界情况处理规范，统计数据准确反映实际资金流动
