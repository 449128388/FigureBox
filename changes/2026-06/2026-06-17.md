## 6. 收藏柜4个空分类实现真实统计逻辑

### 问题背景
我的收藏柜中「预定中」「复数专区」「待出荷」「本命角色」4个分类一直显示"0 体 · 暂无数据"，卡片无实际内容。

### 解决方案
后端 `cabinets.py` 根据各分类的业务语义，从 Orders、AssetTransaction 等表中查询真实数据替换硬编码空数据，前端保持原有组件结构不变。

### 实现逻辑
- **预定中（空气谷）**：查询 `orders` 表中 `order_type='定金预定'` 且 `status IN ('未支付', '已支付')` 的订单，按 `figure_id` 去重，返回对应的手办信息，`purchase_price` 取定金金额
- **复数专区**：查询 `asset_transactions` 中 `remaining_quantity > 0` 的记录，按 `figure_id` 分组并 `SUM(remaining_quantity) >= 2`（同一款手办持仓 2 体以上），返回对应的手办信息
- **待出荷**：查询 `orders` 表中 `status='已完成'`（钱已付清）的订单，按 `figure_id` 去重，返回对应的手办信息，`purchase_price` 取定金+尾款之和
- **本命角色**：查询 `asset_transactions` 中已入库且有持仓的手办，按 `figure.work` 字段分组聚合，`count` 为不同作品数，`items` 为各作品的代表性手办（名称格式：`作品名 (X 体)`）

### 结果
- 4个分类卡片展示真实数据，不再显示"暂无数据"
- 卡片点击进入详情可查看具体藏品列表

## 7. 修复收藏柜各分类陪伴天数计算策略

### 问题背景
各收藏柜头部统计的"陪伴天数"计算策略不统一，复数专区误用了 AVG（应 SUM）、本命角色硬编码为 0（应 SUM）、本命角色 items 中 holding_days 也为 0 导致聚合无效。

### 解决方案
按分类语义统一调整计算策略：情感沉淀类的用 SUM（总陪伴天数），统计观察类的用 AVG（平均陪伴天数），空气类的不显示。

### 实现逻辑
- **复数专区（dup）**：`companion_days` 从 `calc_avg_days` 改为 `calc_total_days`——复数藏品是同一份爱的多份拷贝，累计总天数更有意义
- **本命角色（role）**：
  - `companion_days` 从硬编码 `0` 改为 `calc_total_days(role_figures, 'holding_days')`，遍历 work 组下所有手办查询首次入库日期计算陪伴天数并累加
  - `holding_days` 从 `0` 改为 `total_group_days`，取该 work 组下所有手办的陪伴天数之和

### 最终计算策略对照

| 分类 | 计算方式 |
|------|----------|
| 海景房专区 | SUM（总陪伴天数） |
| 最近入柜 | AVG（平均陪伴天数） |
| 修复工坊 | AVG（平均陪伴天数） |
| 已出藏品 | AVG（平均陪伴天数） |
| 复数专区 | SUM（总陪伴天数） |
| 本命角色 | SUM（总陪伴天数） |
| 预定中 / 待出荷 | 不显示（0） |

### 结果
- 各分类陪伴天数按语义正确计算，复数专区和本命角色不再显示 0

## 8. 优化收藏柜详情各分类默认排序策略

### 问题背景
进入不同收藏柜详情时，排序维度与方向固定（海景房按喜爱度降序，其余按名称升序），未按各分类的特性做差异化排序。

### 解决方案
将 `getDefaultSortByCabinet` 从 if/else 分支改为配置表驱动，为每个分类配置独立的默认排序维度和方向。

### 实现逻辑
- **useCabinetDetail.js**：`getDefaultSortByCabinet` 方法改为 `{ key: { sortBy, sortOrder } }` 配置表，按分类语义配置：

  | 收藏柜 | 默认排序维度 | 默认方向 | 理由 |
  |-------|------------|---------|------|
  | 海景房专区 | 喜爱度 | 降序 | 用户标记的珍爱藏品，进来先看最爱的 |
  | 最近入柜 | 入手时间 | 降序 | 刚入库的新成员在前，符合"最近"语义 |
  | 修复工坊 | 收藏天数 | 降序 | 陪伴最久的病号优先展示 |
  | 已出藏品 | 入手时间 | 降序 | 最近出手的在前，方便回顾流转 |
  | 预定中 | 入手时间 | 升序 | 最早下单的空气谷在前，等最久的优先关注 |
  | 复数专区 | 名称 | 升序 | 同款复购按名字归类，方便定位 |
  | 待出荷 | 入手时间 | 升序 | 最早付清的在前，优先盯进度 |
  | 本命角色 | 入手时间 | 降序 | 按收集时间线展示，最新入手的在前 |

### 结果
- 8 个分类详情页进入时自动按最佳排序展示，提升浏览体验

## 16. 修复收藏历程中卖出单价取错数据源的问题

### 问题背景
收藏历程中卖出记录的单价显示的是成本价（与买入价一致），而非实际卖出价格，导致用户看到的价格与真实交易不符。

### 解决方案
卖出交易的 `AssetTransaction.price` 存储的是成本价，实际卖出价格需从关联的 `SoldOrder.sell_price` 获取。在 `CollectorTransactionService` 中增加对 sell 类型交易的特殊处理，通过 `sold_order_id` 关联查询实际售价并计算单价。

### 实现逻辑
- **collector_transaction_service.py**：
  - 对于 `transaction_type == 'sell'` 的记录，通过 `t.sold_order_id` 查询关联的 `SoldOrder`
  - 取 `sold_order.sell_price / sold_order.quantity` 作为实际卖出单价
  - 若无关联 `SoldOrder` 则回退到 `t.price`
  - `total_amount` 同步更新为 `unit_price * quantity`

### 结果
- 收藏历程中卖出记录正确显示实际卖出价格，与真实售价一致

## 18. 修复收藏历程中补仓记录标签显示，区分补仓与普通买入

## 19. 修复 adjust 类型交易记录未校验订单状态的问题

### 问题背景
在编辑订单（修改定金/尾款金额）时，`asset_transactions` 表中会无条件写入 `adjust` 类型的调整记录。但此表记录的是库存账，只有订单状态为"已完成"（代表已入库）时才应记录成本调整。对"已支付""已取消"等状态的订单写入 adjust 记录会导致库存账数据不准确。

### 解决方案
在 `order_crud_service.py` 的 `update_order` 方法中，将调整记录创建逻辑包裹在 `if db_order.status == "已完成"` 条件中，只有已完成订单的定金/尾款变更才会写入 `asset_transactions`。

### 实现逻辑
- **order_crud_service.py**：在调整记录创建块前加上条件判断 `if db_order.status == "已完成"`
  - 状态为"已完成" → 正常创建 adjust 记录（记录定金/尾款变更导致的成本调整）
  - 状态不为"已完成" → 跳过 adjust 记录创建，不影响库存账

### 结果
- 未完成的订单编辑定金/尾款不再污染 `asset_transactions` 表
- 已完成订单的成本调整逻辑保持不变
