### 14. 重写 HPI 核心计算公式，对齐需求定义

**解决方案：** 之前 HPI 采用「总基准市值法」（HPI = 1000 × 当前总市值 / 总基准市值），与需求定义「HPI = 1000 × (1 + 加权平均收益率)」不一致。虽然单次买入场景数值等价，但多次买入/补仓场景下权重口径存在偏差。

**实现逻辑：**
- **权重口径修正**：权重基座从 `首次买入价 × 订单数` 改为 `历史交易金额（SUM deposit+balance）`，对齐「权重 = 该手办历史交易金额 / 历史总交易金额」
- **HPI 公式重写**：
  - 收益率 = `(当前市场价 - 首次买入价) / 首次买入价`
  - 加权平均收益率 = Σ(收益率 × 权重)
  - HPI = 1000 × (1 + 加权平均收益率)
  - 涨跌点数 = HPI - 1000，涨跌百分比 = 加权平均收益率 × 100%
- **走势图贡献拆分**：在柜/已出贡献改用 `1000 × 当前价/首次价 × 权重` 标尺（0~1000），保持 `HPI = 在柜贡献 + 已出贡献` 恒等式
- **成分表入库**：`contribution` 字段存储百分比点数贡献（如 +13.7），`weight` 字段保持小数权重

### 结果
- 权重基座与需求完全对齐，多次买入/不同价格场景计算正确
- HPI 公式精确匹配：HPI = 1000 × (1 + 加权平均收益率)
- 走势图拆分逻辑不变，在柜/已出双线曲线不受影响
- 已重置表结构并重新跑批

### 15. 修复 HPI 中 total_buy_amount 未考虑币种汇率转换

**解决方案：** `_get_all_traded_figures` 方法中累计买入金额直接用 `SUM(deposit + balance)` 求和，未区分 `deposit_currency` / `balance_currency`。当订单使用非人民币（如 JPY）支付时，日元的数字金额被直接当作人民币累加，导致权重偏移、HPI 失真。

**实现逻辑：**
- 从 SQL 聚合查询改为 Python 层逐订单处理：查询所有有效订单，逐条通过 `CurrencyService.to_cny()` 将 `deposit` 和 `balance` 分别按各自币种转为人民币，再累加到 `total_buy_amount`
- `first_buy_price` 同理：取首条订单的 CNY 总价而非原始金额
- 沿用实时汇率（`CurrencyService.to_cny` 带 `db` 参数），兜底时使用 `FALLBACK_RATES`

### 结果
- 多币种订单的 HPI 计算结果修正，权重回归真实资金占比
- 仅使用人民币下单的用户数据无变化
- 已重置表结构并重新跑批

### 16. 修复 exchange_rate_history 表定时任务未按时执行的问题

**解决方案：** `_fetch_and_save_rates` 使用全局 `threading.Lock` 做并发控制，该锁在 network timeout、进程中断等异常场景下可能残留（未释放），导致后续 09:25 定时任务 `acquire(blocking=False)` 返回 False 而直接跳过，`exchange_rate_history` 表连续多日无新数据。

**实现逻辑：**
- `ExchangeRateService.clear_fetch_lock()`：通过重建 `threading.Lock` 对象来强制清除残留锁，避免 `RuntimeError`
- `ExchangeRateScheduler` 新增每日 00:10 定时任务，调用 `clear_fetch_lock()`，确保锁在 09:25 汇率刷新前一定是干净的

### 结果
- 即使前一日汇率获取因网络异常等原因锁未释放，次日 00:10 自动清除，09:25 正常执行
- exchange_rate_history 表每日正确写入当日汇率数据
