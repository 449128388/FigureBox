### 1. 新增统一汇率服务模块，替换 8 处硬编码汇率字典

**解决方案：** 系统中原有 8 个文件各自定义了相同的硬编码汇率字典（CNY: 1.0, JPY: 1/23, USD: 7.0, EUR: 8.0），汇率更新需逐个修改，容易遗漏。现新增统一汇率服务模块，从中国外汇交易中心 API 获取实时汇率数据，集中管理所有汇率转换。

**实现逻辑：**

**数据模型** `models/exchange_rate.py`：
- `ExchangeRateRealtime`：最新汇率缓存表，每 3 小时刷新，缓存当前所有币种汇率
- `ExchangeRateHistory`：汇率历史记录表，记录每次 API 获取的汇率快照

**服务层** `services/exchange_rate_service/exchange_rate_service.py`：
- `ExchangeRateService.get_exchange_rates(db)`：统一入口，返回所有币种汇率映射（优先缓存 → API → 兜底默认值）
- `ExchangeRateService.get_rate(db, currency)`：获取单币种汇率
- `ExchangeRateService.to_cny(db, amount, currency)`：币种转人民币
- `ExchangeRateService.refresh_from_api(db)`：从 `http://www.chinamoney.com.cn/r/cms/www/chinamoney/data/fx/ccpr.json` 获取实时汇率
- API 请求严格限速：随机延时 3-8 秒 + 单日请求 < 6 次 + 全局并发锁（无并发请求）
- 缓存有效期 3 小时，超时后定时任务才发新请求
- 使用请求头 `User-Agent` + `Referer`

**定时任务** `services/exchange_rate_service/exchange_rate_scheduler.py`：
- `ExchangeRateScheduler`：每 3 小时自动刷新一次汇率（IntervalTrigger 3h）
- 注册到 `scheduler_service/__init__.py` SchedulerManager，应用启动时自动加载

**迁移** `migrations/add_exchange_rate_tables.py`：
- 创建 `exchange_rate_realtime` 和 `exchange_rate_history` 两张表
- 注册到 `entrypoint.sh`，容器启动时自动建表

**替换的 8 个文件：**

| # | 文件 | 替换方式 |
|---|---|---|
| 1 | `collector_activity_service.py` | `PRICE_EXCHANGE_RATES` → `ExchangeRateService.get_rate(db, currency)` |
| 2 | `asset_core_calculations.py` | `EXCHANGE_RATES` → `ExchangeRateService.get_rate(db, currency)` |
| 3 | `profit_analysis_service.py` | 内联 `exchange_rates` dict → `ExchangeRateService.get_rate(db, currency)` |
| 4 | `buy_order_service.py` | `EXCHANGE_RATES` → `ExchangeRateService.get_rate(db, currency)` |
| 5 | `sell_order_service.py` | `EXCHANGE_RATES` → `CurrencyService.get_exchange_rate(currency)` |
| 6 | `transaction_query_service.py` | `EXCHANGE_RATES` → `ExchangeRateService.get_rate(db, currency)` |
| 7 | `currency_service.py` | `EXCHANGE_RATES` → `ExchangeRateService.get_exchange_rates(db)`（当 db 可用时），`FALLBACK_RATES` 兜底 |
| 8 | `figure_price_service.py` | `EXCHANGE_RATES` → `CurrencyService.to_cny(amount, currency)`（通过 CurrencyService 间接使用统一汇率） |

### 结果
- 汇率数据来源统一：中国外汇交易中心实时汇率
- 系统定时自动刷新，无需手动维护硬编码汇率
- 汇率更新一处修改全局生效
- API 不可用时自动降级使用兜底汇率，系统不中断

- **触发器**：`IntervalTrigger(hours=3)`，每 3 小时触发一次
- **启动时机**：应用启动时通过 `SchedulerManager.start_scheduler()` 自动注册

- **API 端点**：`http://www.chinamoney.com.cn/r/cms/www/chinamoney/data/fx/ccpr.json`，请求头含 `User-Agent` + `Referer`

### 4. 修复汇率服务首次未获取数据 + API 解析格式错误 + 表空数据

**解决方案：** 三个问题导致 exchange_rate_realtime 和 exchange_rate_history 表始终为空：
1. 调度器 `next_run_time=None` 阻止了首次触发，需等待完整间隔才执行
2. `_parse_response` 假想的 API 字段（`data` 数组、`enName`、`value`）与实际 API 返回（`records` 数组、`vrtEName`、`price`）完全不匹配
3. 无首次启动即时获取逻辑

**实现逻辑：**

**问题一** `exchange_rate_scheduler.py`：
- `next_run_time=None` 改为移除该参数，APScheduler 自动在启动后立即触发首次执行（无需等待 3 小时间隔）
- `start_scheduler()` 内新增启动后立即调用 `refresh_exchange_rates()` 一次，确保首次数据在服务启动时即刻写入

**问题二** `exchange_rate_service.py` `_parse_response`：
- 数据路径：原 `data.get("data", [])` → 改为优先取 `data["records"]`（实际字段），回退 `data["data"]`（备用格式）
- 字段名：原 `enName`/`value` → 改为取 `vrtEName`（实际字段，如 `100JPY/CNY`），回退 `enName`
- 价格字段：原 `value` → 改为取 `price`（实际字段），回退 `value`
- 请求 JSON 解析容错：增加捕获 `response.json()` 异常及字符串二次解析

**真实 API 返回结构（2026-06-29 实测）：**
```json
{"head":{...},"data":{...},"records":[
  {"vrtEName":"USD/CNY","price":"6.8166",...},
  {"vrtEName":"100JPY/CNY","price":"4.2107",...},
  {"vrtEName":"EUR/CNY","price":"7.7405",...},
  {"vrtEName":"HKD/CNY","price":"0.86942",...},
  {"vrtEName":"GBP/CNY","price":"8.9832",...}
]}
```

**解析后生成的币种汇率：**
- USD = 6.8166, EUR = 7.7405, JPY = 4.2107/100 = 0.042107, HKD = 0.86942, GBP = 8.9832, 以及 CNY = 1.0

### 结果
- 应用首次启动即自动获取汇率数据并写入数据库
- `exchange_rate_realtime` 和 `exchange_rate_history` 表有数据
- 定时任务每 3 小时刷新一次

### 6. 汇率定时任务按中间价政策规则优化

**解决方案：** 原定时任务每 3 小时执行一次，不符合中国外汇交易中心中间价发布规则——仅工作日 09:25 发布一次，全天有效。

**实现逻辑：**

**定时任务** `exchange_rate_scheduler.py`：
- **触发器**：`IntervalTrigger(hours=3)` → `CronTrigger(day_of_week='mon-fri', hour=9, minute=25)`，仅工作日上午 09:25 触发一次
- **交易日判断**：新增 `is_trading_day()` 函数，同时检查周末（weekday >= 5）和 2026 年中国法定节假日（春节、国庆、元旦等）
- **启动逻辑** `start_scheduler()`：
  - 当前为交易日且已过 09:25 → 立即执行首次获取
  - 当前为交易日但未到 09:25 → 等待定时触发
  - 当前非交易日 → 跳过首次获取
- **执行逻辑** `refresh_exchange_rates()`：双重检查（交易日 + 时间 >= 09:25），非交易日或未到发布时点直接跳过

**缓存策略** `exchange_rate_service.py`：
- 移除固定 `CACHE_DURATION_HOURS = 3`
- `_get_cached_rates()` 改为按中间价规则判断：
  - 缓存数据是当日获取的且已过 09:25 → 全天有效
  - 缓存数据是之前交易日获取的且今日未到 09:25 → 继续沿用
  - 其他情况（今日已过 09:25 但缓存不是今天的）→ 缓存过期，需刷新

### 结果
- 定时任务仅在交易日 09:25 执行一次汇率获取
- 非交易日（周末/节假日）不执行
- 获取到的汇率全天有效，缓存到下一个交易日 09:25 前

### 12. 塑料小人指数(HPI)重新设计：投资生涯全周期收益指数

**解决方案：** 将 HPI 从"全站行业大盘"重新定位为"用户塑料投资生涯全周期收益指数"，核心差异化在于已出手办永不剔除、继续跟踪当前市场价。

**计算公式：**
- HPI = 1000 × (1 + 平均超额收益率)
- 平均超额收益率 = Σ(每手办收益率 × 该手办权重)
- 每手办收益率 = (当前市场价 - 首次买入价) / 首次买入价
- 权重 = 该手办历史交易金额 / 历史总交易金额

**实现逻辑：**

**数据模型** `models/hpi.py`：
- `HPIDaily`：hpi_daily 表，每日快照（指数值、盈亏分布、卖飞/卖对统计）
- `HPIComponent`：hpi_components 表，成分股明细（买入价、市价、收益率、权重、卖飞标记）

**服务层** `hpi_service.py`：
- `get_hpi_dashboard()`：获取最新 HPI（优先快照，无则实时）
- `get_hpi_history()`：获取历史 K 线数据
- `get_components()`：获取成分股详情
- `run_daily_batch()`：每日跑批计算
- `_calculate_hpi()`：核心计算（从 Order 获取用户所有交易过的手办，从 Figure 获取市价，从 SoldOrder 判断已出）

**定时任务** `hpi_scheduler.py`：`CronTrigger(hour=0, minute=30)`，每日 00:30 遍历所有活跃用户跑批

**API** `market/dashboard.py`：
- `GET /dashboard`：返回 HPI 核心数据
- `GET /hpi-history`：返回历史 K 线数据
- `GET /hpi-components`：返回成分股详情

**前端** `HPIDetail.vue`：
- 指数核心指标卡片（HPI 值、平均收益率、在柜/已出数）
- K 线图（ECharts）：绿色实线在柜、灰色虚线已出、绿色渐变面积填充
- 时间轴：近7天/近30天/近1年/全部 切换
- 成分股列表：在柜/已出、收益率、权重、卖飞/卖对标记

### 结果
- HPI 回答「从我买入每一体手办那天起，它们后来平均涨了多少？」
- 已出手办永久保留跟踪，量化"卖飞后悔值"
- 每日 00:30 自动跑批持久化

### 14. 修复 HPI 涨平跌统计逻辑：添加 ±1% 容差阈值 + 药丸样式对齐

**解决方案：** 原 HPI 涨跌平统计使用 `return_pct > 0` 作为"涨"判定，微小价格波动（如 ¥1,280→¥1,281，涨幅 0.08%）也会被计入"涨"或"跌"，不符合实际投资体验。同时前端展示样式与设计稿不一致。

**实现逻辑：**
- **后端** `hpi_service.py` `_calculate_hpi()`：涨跌平判定添加 `THRESHOLD = 1.0`（±1% 容差），`return_pct > 1.0` 为涨，`return_pct < -1.0` 为跌，中间区域判平

### 17. 修复 HPI 首次买入价取值：同一手办多次购买时取最低价而非最早订单价

**解决方案：** SQL 中 `MIN(o.deposit + o.balance) AS first_buy_price` 返回的是所有订单中 `deposit+balance` 的**最小数值**，而非最早订单的价格。如果用户同一个手办买了两次且第二次价格更低（例如补仓），首次买入价会被错误地取为更低的价格，导致收益率虚高。

**实现逻辑：**
- **`_get_all_traded_figures`** SQL 查询：将 `MIN(o.deposit + o.balance)` 替换为关联子查询 `(SELECT o2.deposit + o2.balance FROM orders o2 WHERE … ORDER BY o2.created_at ASC LIMIT 1)`，确保从该手办最早的订单中取价格

### 结果
- 同一手办多次购买时，首次买入价始终取第一次购买的价格，收益率计算正确
- 补仓场景（第二次价格更低或更高）不再出现收益率虚高或虚低

### 18. 修复汇率表未按日更新：exchange_rate_history 和 exchange_rate_realtime 停留在首次部署时间

**解决方案：** `_check_daily_limit` 统计 `ExchangeRateHistory` 记录数，每次 API 请求写入 N 个币种记录（6条），而 `DAILY_REQUEST_LIMIT = 6`，一次成功请求即耗尽当日配额，导致后续（含 cron 下次触发前的容器重启）均被拦截，数据永远停留在首次部署时间。

**实现逻辑：**
- **`_check_daily_limit`** `exchange_rate_service.py`：改用 `ExchangeRateRealtime.updated_at >= today` 计数，**有任意一条实时汇率记录即视为今日已获取**，避免按币种记录数重复计费
- **`_fetch_and_save_rates`**：入口处优先调用 `_get_cached_rates()` 检查缓存有效性，已有今日有效数据时直接跳过不消耗配额

### 结果
- 09:25 cron 成功后任何容器重启不再覆盖当日数据、不消耗配额
- 09:25 cron 失败时配额仍可用，下次请求能正常触发重试
