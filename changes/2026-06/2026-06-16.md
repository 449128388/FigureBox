  - 修改 `get_valid_orders` 函数，增加 `user_id` 参数过滤当前用户数据

  - 左卡片：显示 🧸 图标，标题"藏品总数"，数值+单位"体"，底部文案"覆盖 X 个角色 / Y 个 IP"

  - 右卡片：显示 📤 图标，标题"已出藏品"，数值+单位"体"，底部显示"陪伴时长 X 天"
  - 样式参考 `collector_mode.html` 的 `summary-card` 设计：白色背景、圆角12px、阴影效果、悬停上浮动画

### 结果

## 3. 修复收藏家看板 API 500 错误

### 问题背景
访问 `/api/collector/dashboard` 接口时报 500 错误，后端抛出 `AttributeError: 'Figure' object has no attribute 'character'` 异常。

### 解决方案
修正后端代码中引用了不存在的 `Figure.character` 属性，改为使用实际存在的 `Figure.work` 字段，并同步更新前端展示文案。

### 实现逻辑
- **根因分析**：`dashboard.py` 中使用了 `fig.character` 获取手办角色信息，但 `Figure` 模型实际没有 `character` 字段，只有 `work`（作品出处）字段
- **后端修复**：
  - 将 `unique_characters = set(fig.character for fig in figures if fig.character)` 改为 `unique_works = set(fig.work for fig in figures if fig.work)`
  - 将返回字段 `unique_characters` 改为 `unique_works`
- **前端修复**：
  - 将展示文案"覆盖 X 个角色 / Y 个 IP"改为"覆盖 X 个作品 / Y 个厂商"
  - 将数据绑定从 `collectorData?.summary?.unique_characters` 改为 `collectorData?.summary?.unique_works`

### 结果
- `/api/collector/dashboard` 接口恢复正常，不再返回 500 错误
- 藏品总数卡片底部文案改为"覆盖 X 个作品 / Y 个厂商"，与数据模型一致

## 7. 拆分收藏家看板 API 接口

### 问题背景
原 `/api/collector/dashboard` 接口返回数据量较大，包含顶部概览、收藏柜、标签云、收藏历程等多个模块的数据，不利于前端按需加载和缓存优化。

### 解决方案
按照页面模块拆分原接口为4个独立接口，每个接口职责单一，支持前端按需请求和并行加载。

### 实现逻辑
- **接口拆分规划**：
  | 序号 | 接口地址 | 对应页面模块 | 职责 |
  | :-: | ----------------------------- | ------------ | ------------- |
  | 1 | `GET /api/collector/summary` | 顶部概览 + 三指标卡片 | 用户基础信息 + 藏品统计 |
  | 2 | `GET /api/collector/cabinets` | 我的收藏柜（高价值藏品） | 分类橱窗卡片 |
  | 3 | `GET /api/collector/tags` | 标签云 | 多维分组筛选标签 |
  | 4 | `GET /api/collector/timeline` | 收藏历程（动态流） | 时间线动态列表 |

- **后端实现**：
  - 创建 `summary.py`：处理藏品总数、本月新入柜、已出藏品等统计数据
  - 创建 `cabinets.py`：处理高价值藏品列表（海景房、小赚、破发、已转卖）
  - 创建 `tags.py`：处理标签云数据（海景房、破发区、待补款、已出坑计数）
  - 创建 `timeline.py`：处理收藏历程动态流（最近5条订单记录）
  - 更新 `collector_router.py`：注册4个新路由，保留原 `/dashboard` 接口兼容

- **前端实现**：
  - 修改 `useCollectorData.js`：使用 `Promise.all` 并行请求4个接口
  - 合并4个接口返回数据为统一格式，保持组件层无需修改

### 结果
- 原 `/api/collector/dashboard` 接口保留兼容，仍可正常访问
- 新增4个独立接口，支持前端按需加载和缓存优化
- 前端使用并行请求，提升数据加载效率

## 11. 修复各收藏柜陪伴天数计算逻辑（按分类区分 SUM/AVG/不显示）

### 问题背景
各收藏柜的"陪伴天数"计算逻辑未按分类特性区分，统一使用总和（SUM）或硬编码为 0，不符合实际语义。需要根据每个收藏柜的情感含义和业务场景，采用不同的统计口径。

### 解决方案
按分类特性分别采用总和（SUM）、平均值（AVG）或不显示三种策略，并补全修复工坊的 `holding_days` 计算。

### 实现逻辑
- **后端修改**（`backend/app/api/collector/cabinets.py`）：
  - 新增 `calc_avg_days(items, field)` 工具函数，计算 items 列表中指定字段的平均值（四舍五入取整）
  - 修复工坊分类补全 `holding_days` 计算：查询每条藏品的首次入库日期（`asset_transactions`），计算（当前日期 - 首次入库日期）的天数
  - 各分类陪伴天数调整：

    | 分类 | 计算方式 | 实现 |
    | --- | --- | --- |
    | 海景房专区 | 总陪伴天数（SUM） | `calc_total_days(star_figures, 'holding_days')` — 不变 |
    | 最近入柜 | 平均陪伴天数（AVG） | `calc_total_days` → `calc_avg_days` |
    | 修复工坊 | 平均陪伴天数（AVG） | 硬编码 `0` → `calc_avg_days(repair_figures, 'holding_days')` |
    | 已出藏品 | 平均陪伴天数（AVG） | `calc_total_days` → `calc_avg_days` |
    | 复数专区 | 总陪伴天数（SUM） | 保持 `0`（暂无数据） |
    | 本命角色 | 总陪伴天数（SUM） | 保持 `0`（暂无数据） |
    | 预定中 | 不显示 | 保持 `0` |
    | 待出荷 | 不显示 | 保持 `0` |

- **前端修改**（`frontend/.../CabinetDetail.vue`）：
  - 预定中（`air`）和待出荷（`wait`）两个分类隐藏"陪伴天数"统计块，使用 `v-if="cabinet.key !== 'air' && cabinet.key !== 'wait'"` 控制显隐
  - 其他分类正常显示陪伴天数

### 结果
- 各收藏柜的陪伴天数按语义正确计算：总沉淀（海景房、复数、本命）、平均时长（新入柜、修复、已出）、不显示（空气谷）
- 修复工坊的陪伴天数从 0 变为正确的平均陪伴天数
- 预定中/待出荷不再显示无意义的 "0 / -" 陪伴天数

- **默认排序方向调整**：

## 22. 修复收藏柜详情喜爱度评分无法保存的问题

### 问题背景
收藏家模式>我的收藏柜>收藏柜详情中，点击藏品卡片上的星星无法更新喜爱度评分，F12 网络面板中无 POST 请求发出。

### 解决方案
Vue 3 中，子组件若未通过 `emits` 选项声明自定义事件，父组件上的 `v-on` 监听器会被当作原生 DOM 事件（fallthrough attribute）挂载到根元素上。`StarRating` 发出的 `$emit('set-rating')` 是 Vue 内部自定义事件，不会触发原生 DOM 事件监听器，导致 `@set-rating` 回调永不被执行。为 `StarRating` 和 `FigureGrid` 补充 `emits` 声明，让 Vue 3 正确识别这些为自定义事件。

### 实现逻辑
- **StarRating.vue**：新增 `emits: ['click', 'set-rating']` 声明，使 `$emit('set-rating')` 能被父组件的 `@set-rating` 正确接收
- **FigureGrid.vue**：新增 `emits: ['toggle-star', 'set-rating', 'view-detail', 'sell']` 声明，确保自定义事件在组件层级间可靠传递
- 保留上一轮对 `CabinetDetail.vue` 中 `this.$axios` / `this.$message` 的修复（导入 axios 和 ElMessage）和 `useCabinetDetail.js` 中移除 setTimeout 延迟的优化

### 结果
- 点击藏品卡片星星后立即发出 POST 请求到 `/api/collector/ratings`，评分正常保存
- 收藏柜详情页喜爱度交互全链路可用
