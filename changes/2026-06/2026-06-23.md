# 2026年6月23日 更新日志

## 修复

### 1. 动态流时间格式优化
**解决方案：** 动态流中每条事件的时间只显示到 HH:mm（如"14:30"），缺少秒数，信息不够精确。

**实现逻辑：**
- `useActivityFeed.js` 中 `formatTime` 方法的字符串截取长度从 5 改为 8
- 时间格式从 `HH:mm` 改为 `HH:mm:ss`（如"14:30:00"）
- 后端 `created_at` 字段使用 `.isoformat()` 返回完整时间，前端仅需调整截取逻辑

### 2. 动态流详情弹窗实现
**解决方案：** 点击动态流事件的"查看详情"按钮，后端接口有数据返回，但前端没有对应的详情展示页面。

**实现逻辑：**
- `ActivityFeed.vue` 模板中新增弹窗弹出层，根据 `event_type` 渲染不同布局：
  - BUY：订单信息（订单编号、下单时间、支付类型、已付金额、待补金额、状态）
  - SELL：盈亏卡片（实现盈亏金额/颜色）+ 交易信息（卖出价、成本、盈亏、日期、买家、持有天数）
  - FULL_PAY：付款信息（上次支付、累计支付、支付时间）
  - IN_STOCK：入库信息（入库日期、订单编号、成本、入柜位置）
  - OUT：移出信息（移出分类、原因）+ 提示说明
  - TAG_ADD：标签信息（标签名称、添加时间）
  - ORDER_CANCEL：取消订单信息（编号、时间、原因、退款金额）
  - PRICE_UPDATE：价格变动信息（原价、新价、变动金额、变动幅度）
- 弹窗支持点击遮罩关闭、动画缩放淡入

### 3. 动态流详情弹窗居中显示修复
**解决方案：** 点击动态流事件的"查看详情"按钮后，订单信息弹窗页面出现在底部而非正中心，视觉体验不佳。

**实现逻辑：**
- 将弹窗布局从底部滑出的 Bottom Sheet 改为屏幕正中心显示的 Modal 对话框
- `.sheet-overlay` 的 `align-items` 从 `flex-end` 改为 `center`，使弹窗在视口中垂直居中
- `.sheet` 的宽度从 `100%` 改为 `90%`，最大宽度从 `640px` 调整为 `520px`，更适配居中对话框
- 圆角从顶部单边 `20px 20px 0 0` 改为四周统一 `16px`
- 动画从底部上滑 `sheetUp` 改为缩放淡入 `modalIn`（`opacity + scale`），符合居中弹窗的视觉预期

### 4. 动态流详情弹窗标题统一为「动态流详情」
**解决方案：** 弹窗标题之前动态显示手办名称，需求要求统一修改为固定文本"动态流详情"。

**实现逻辑：**
- `detailSheetTitle` 计算属性从返回 `feed.eventDetail.value?.detail_data?.figure_name || '详情'` 改为直接返回 `'动态流详情'`

### 5. 卖出事件详情增加操作按钮
**解决方案：** 当动态流事件类型为"卖出"时，详情页面需要提供"查看资金流水"和"查看手办详情"两个导航按钮。

**实现逻辑：**
- SELL 事件模板中新增 `detail-actions` 按钮区域

### 6. 动态流卖出事件数据缺失修复
**解决方案：** 动态流的卖出事件只统计了状态为"已完成"的卖出订单，导致 activity_feed 表中卖出事件数据不全，所有状态的卖出订单都应被记录。

**实现逻辑：**
- `seed_activity_feed.py` 中 `_seed_sell_events` 方法的查询条件去除 `SoldOrder.status == "已完成"` 的限制，改为只过滤 `is_active == 1`，包含所有状态的卖出订单
- 根据订单状态动态生成事件标题：待发货→等待发货、已发货→已发货、已完成→交易完成、退款/纠纷→退款/纠纷中
- detail_data 中新增 `status` 字段记录当前订单状态，方便前端展示
- 修改完成后需重新执行 seed 脚本回填缺失数据

### 7. 动态流详情手办图片使用实际图片

- 卖出价格颜色从 `green` 改为 `accent`（主题色），避免与盈亏颜色混淆

### 10. 动态流卖出事件收益率和持有天数计算修复
**解决方案：** 卖出事件详情的持有天数始终显示为 0，且缺少收益率统计。将收益率、持有天数、订单号、买家手机号全部预计算后写入 activity_feed.detail_data 快照，请求详情时直接读取不再实时计算。

**实现逻辑：**

- `seed_activity_feed.py` 的 `_seed_sell_events` 在写入前预计算：
  - 收益率 = profit / cost_price × 100，保留两位小数
  - 持有天数 = sold_order.created_at 日期 - figure.purchase_date
  - 订单号 = sold_order.order_number 或 display_order_number
- `get_event_detail` 移除 SELL 事件专属的实时计算和 SoldOrder 关联查询代码块，所有数据直接从 `detail_data` 返回

**解决方案：** 在已出售订单中新增出售订单后，动态流没有自动新增对应的 SELL 事件数据，需要事件驱动在业务完成后自动写入。

**解决方案：** 编辑已出售订单后，activity_feed 表中的 SELL 事件数据未同步更新，导致动态流详情与订单实际数据不一致。

- 更新操作与订单更新在同一事务中，确保数据一致性

### 15. activity_feed 表新增 updated_at 时间戳
**解决方案：** activity_feed 表缺少 updated_at 字段，无法追踪数据的最后更新时间。新增记录时 updated_at 应与 created_at 一致，更新时应记录修改时间。

**实现逻辑：**
- `activity_feed` 模型新增 `updated_at` 列，类型为 `TIMESTAMP`，默认值 `CURRENT_TIMESTAMP`，设置 `onupdate=func.now()` 自动在 ORM 层面触发更新时间
- `record_event` 方法在创建记录时显式传入 `updated_at=now`，确保与 `created_at` 值一致
- MySQL 层级设置 `ON UPDATE CURRENT_TIMESTAMP`，双重保障更新时自动记录时间
- 创建迁移脚本 `add_activity_feed_updated_at.py`，通过 `ALTER TABLE` 为已有表添加字段

### 32. 修复 `/api/collector/timeline` 接口 500 Internal Server Error
**解决方案：** 访问动态流列表接口时返回 500 错误，原因是 activity_feed 表数据量增长后，MySQL 排序操作超出 `sort_buffer_size` 限制（Error 1038: Out of sort memory）。

**实现逻辑：**
- 创建数据库迁移脚本 `add_activity_feed_user_created_index.py`
- 为 `activity_feed` 表添加 `idx_activity_feed_user_created` 复合索引（`user_id, created_at DESC`）
- MySQL 可以利用索引顺序直接检索和排序，避免在内存中执行 filesort 操作，从根本上解决了大数据量下的排序内存溢出问题

### 42. 修复订单从"未支付"变更为"已完成"时缺少尾款资金流水

**解决方案：** 在尾款管理中将订单尾款状态从"未支付"变更为"已完成"时，order_transactions 表中缺少尾款的资金流水记录，原因是已有定金记录导致整个尾款创建逻辑被跳过。

**实现逻辑：**
- **根因分析**：`update_order` 方法中原本使用 `if not existing_txn` 判断是否已有初始资金流水记录，但该查询不区分交易类型（deposit/balance），订单创建时已写入定金记录，导致编辑时尾款记录被跳过
- **修复内容**：将单一检查拆分为独立检查——定金部分按 `transaction_type == "deposit"` 查询并补充缺失记录；尾款部分增加 `db_order.status != "未支付"` 条件后按 `transaction_type == "balance"` 查询并补充缺失记录

### 结果
- 订单从"未支付"变为"已完成"时，尾款资金流水记录正确创建
- 已有定金记录不受影响，不会重复创建
