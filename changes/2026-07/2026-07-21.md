## 缺陷修复

### 1. 修复涂装师字段含下划线 `_` 字符保存失败的缺陷

**解决方案：** 涂装师（如 HPOI 数据 `_Gallun`）中常含下划线 `_` 字符，`schemas/figure.py` 的 `ALLOWED_CHARS_PATTERN` 正则未将下划线列入允许字符集，导致「_Gallun、Hato」中前缀下划线被识别为非法字符，触发「涂装包含不允许的字符」校验失败。

**实现逻辑：**

- **后端** `schemas/figure.py` 的 `ALLOWED_CHARS_PATTERN`：在字符类中追加 `\_`（下划线 U+005F），与 `.` `,` `:` `;` 等符号并列
- 该修复同时适用于「原画作者」「作品出处」等其他复用 `ALLOWED_CHARS_PATTERN` 的字段，避免后续含下划线人名再次触发相同校验

### 2. 修复全款预定订单已入库时支付时间显示错误的缺陷

**解决方案：** 资产看板交易流水查看买入订单时，订单类型为「全款预定」且状态为「✅ 已入库」时，原代码仅在 `is_spot` 或 `order_type == "定金预定"` 分支覆写支付明细日期，全款预定订单没有专属分支，导致支付时间字段从交易记录（`OrderTransaction.transaction_date`）取值，与实际一次性付清时的 `orders.payment_time` 不一致。

**实现逻辑：**

- **后端** `buy_order_service.py` 的 `_get_payment_details`：
  - 在「定金预定」分支之后新增「全款预定」分支：`order.order_type == "全款预定" and order.status == "已完成"`
  - 遍历 payment_items，若 `order.payment_time` 非空则覆写 `item["date"]` / `item["full_date"]` 为该时间（YYYY-MM-DD / YYYY-MM-DD HH:MM:SS 两种格式）
  - 同时将 `item["method"]` 覆写为 `order.payment_method`（全款一次性付清仅对应一个支付方式）
  - 全款预定为一次性付清，无定金/尾款拆分，无需 status 分支判断

### 3. 修复板块涨幅排行排序逻辑缺陷

**解决方案：** 资产看板「行情-板块涨幅排行」当前按 `abs(change)` 绝对值降序排列，可能出现「高涨幅板块排后面、低跌幅板块排前面」的反直觉情况（如 -50% 跌停排第一，+1% 微涨排最后）。需要保证「涨的优先于跌的」，涨跌幅相同时按数值大小排序。

**实现逻辑：**

- **后端** `sector_service.py` 的 `get_user_sector_ranking`：
  - 将原 `sectors.sort(key=lambda x: abs(x["change"]), reverse=True)` 改为三段式排序：
    1. 将所有板块按 `change > 0` / `change < 0` 拆分为 `positive_sectors` / `negative_sectors`
    2. `positive_sectors` 按 `change` 降序排列（涨幅从高到低）
    3. `negative_sectors` 按 `change` 降序排列（数值降序 = -1 > -5 > -10，跌幅从小到大）
  - 拼接 `positive_sectors + negative_sectors` 后取前 `limit` 个
  - 三种业务场景自动满足：
    - 当涨幅>0 板块数 > limit：仅展示涨幅>0 板块，按涨幅从高到低
    - 当 0 < 涨幅>0 板块数 <= limit：先展示所有涨幅>0，再补足跌幅<0（按跌幅从小到大）
    - 当涨幅>0 板块数 == 0：仅展示跌幅<0，按跌幅从小到大

### 4. 修复卖出订单详情接口 500 内部错误的缺陷

**解决方案：** 资产看板交易流水查看卖出订单详情时，接口 `GET /api/trade_records/sell-order/{id}` 返回 500 错误。`SellOrderService.get_order_detail` 内部使用 `Figure` 模型查询手办信息（`db.query(Figure).filter(Figure.id == figure_id).first()`），但文件顶部 import 区域仅引入了 `SoldOrder`，未引入 `Figure`，导致请求时抛出 `NameError: name 'Figure' is not defined`。

**实现逻辑：**

- **后端** `sell_order_service.py`：
  - 在 import 区域新增 `from app.models.figure import Figure`，补齐模型引用
  - 原文件只引用了 `SoldOrder` 和 `CurrencyService`，缺少 `Figure` 引入，应为之前重构时遗漏的 import
  - 该修复让 `get_order_detail` 中根据 `figure_id` 查询 Figure 实例以填充手办名称和图片的逻辑可正常执行

### 5. 修复 sold_orders 表字段注释乱码的缺陷

**解决方案：** 通过 PowerShell 执行 ALTER TABLE 添加字段时，中文注释在命令行编码转换中出现乱码，导致 `payment_method` 和 `sell_date` 字段的 COMMENT 被存储为乱码字符。使用 Python 脚本（pymysql 驱动，utf8mb4 字符集）重新设置字段注释，确保中文正确写入数据库。

**实现逻辑：**

- **后端** `scripts/fix_column_comments.py`：
  - 使用 pymysql 以 utf8mb4 字符集连接数据库，避免终端编码问题
  - 对 `sold_orders` 表执行 `ALTER TABLE MODIFY COLUMN`，重新设置 `payment_method` 和 `sell_date` 的 COMMENT
  - 脚本可通过 `docker exec` 在容器内执行完成修复

### 6. 修复 sell_date 字段类型导致 Pydantic 反序列化失败的缺陷

**解决方案：** 接口 `GET /api/sold-orders/{id}` 返回 500 错误，Pydantic 报错「Datetimes provided to dates should have zero time」。原因是 `sell_date` 字段在 Schema 中定义为 `date` 类型，但前端日期选择器可能传入含时间的 datetime 字符串，导致 Pydantic 反序列化时因时间部分非零而校验失败。将 `sell_date` 从 `date` 改为 `datetime` 类型，支持精确到秒的时间存储。

**实现逻辑：**

- **后端 Model** `models/sold_order.py`：`sell_date` 列类型从 `Date` 改为 `DateTime`
- **后端 Schema** `schemas/sold_order.py`：`SoldOrderBase` 和 `SoldOrderUpdate` 中 `sell_date` 类型从 `date` 改为 `datetime`；新增 `validate_sell_date` 校验器处理空字符串转型
- **前端** `CreateSellOrderDrawer.vue`：日期选择器 `type` 从 `date` 改为 `datetime`，新增 `format` 和 `value-format` 为 `YYYY-MM-DD HH:mm:ss`
- **前端** `BasicInfoTab.vue`：同上，日期选择器改为 `type="datetime"`，格式化为 `YYYY-MM-DD HH:mm:ss`
- **数据库** `sold_orders` 表：执行 `ALTER TABLE MODIFY COLUMN sell_date DATETIME` 将列类型从 `DATE` 改为 `DATETIME`

### 7. 修复 payment_method 字段 NULL 导致响应序列化失败的缺陷

**解决方案：** 接口 `GET /api/sold-orders/{id}` 返回 500 错误，Pydantic 报错「Input should be a valid string, input: None」。原因是 `payment_method` 字段在 Schema 中定义为 `str`（非可选类型），但数据库中已有订单的 `payment_method` 为 NULL，Pydantic 序列化响应模型时因类型不匹配而校验失败。将 `payment_method` 改为 `str | None = None` 可选类型，允许 NULL 值正常序列化。

**实现逻辑：**

- **后端 Schema** `schemas/sold_order.py`：`SoldOrderBase` 中 `payment_method` 类型从 `str = ""` 改为 `str | None = None`，允许响应序列化时接收 NULL 值

### 8. 修复创建/更新已出售订单时 payment_method 和 sell_date 未写入数据库的缺陷

**解决方案：** 在尾款管理模块（SoldOrders）中创建或编辑已出售订单时，`payment_method` 和 `sell_date` 虽然已在前端表单增加、Schema 中定义、Model 中声明，但 CRUD 服务层在构造 `SoldOrder` 对象时遗漏了这两个字段的赋值，导致数据未持久化到数据库。

**实现逻辑：**

- **后端** `sold_order_crud_service.py`：
  - `create_sold_order`：在 `SoldOrder()` 构造函数中新增 `payment_method=order_data.payment_method` 和 `sell_date=order_data.sell_date` 参数
  - `update_sold_order`：在字段更新区块中新增 `if order_data.payment_method is not None:` 和 `if order_data.sell_date is not None:` 两个赋值分支

### 9. 修复编辑已出售订单时 payment_method 和 sell_date 字段未在前端展示的缺陷

**解决方案：** 尾款管理模块编辑已出售订单时，`payment_method` 和 `sell_date` 虽然已存入数据库，但订单列表查询（`get_sold_orders`）手动构造 `SoldOrderListItem` 响应对象时未传入这两个字段，导致前端编辑弹窗无法获取已有数据并回显。

**实现逻辑：**

- **后端** `sold_order_query_service.py`：在 `SoldOrderListItem()` 构造函数中新增 `payment_method=order.SoldOrder.payment_method` 和 `sell_date=order.SoldOrder.sell_date` 参数

### 10. 修复查看卖出订单时成交时间取值错误的缺陷

**解决方案：** 资产看板交易流水查看卖出订单时，订单类型为「【卖出】」且状态为「✅ 已入库」时，「订单信息」中的「成交时间」原使用 `sold_orders.created_at`（记录创建时间），并非用户设置的实际卖出时间。应使用 `sold_orders.sell_date` 字段展示真实的成交时间。

**实现逻辑：**

- **后端** `sell_order_service.py`：`get_order_detail` 中 `transaction_date` 字段的数据源从 `sold_order.created_at` 改为 `sold_order.sell_date`，若 `sell_date` 为空则降级显示 `"-"`
