### 6. 投资复盘统计逻辑核验与边界修复

  - 同步修正 components 中 `sell_right` 字段写入逻辑，与 sell_fly 互斥且能完整覆盖所有已出体
- **前端 `InvestmentReview.vue`**：
  - 投资胜率展示从 `Math.round` 整数百分比改为 `toFixed(1)` 一位小数（如 66.7%）
  - 投资胜率分母从 `soldUp + soldDown` 改为 `soldItems.length`（真正的已出体总数），与规范「卖对体数 / 已出体总数」一致

### 11. 修复 `/api/market/sector-ranking` 500 错误

**解决方案：** 后端遍历 `db.query(HPIComponent, ...)` 多实体查询结果时，误将 SQLAlchemy 2.x 的 `Row` 对象当作字典用 `row._mapping.get(dimension)` 访问，且 `isinstance(row, tuple)` 对 Row 恒为 False，导致 `comp` 仍是 Row 而非 `HPIComponent`，访问 `comp.weight` 抛 `AttributeError`。

**实现逻辑：**
- 统一通过 `row[0]` 取 `HPIComponent` 实例（Row 原生支持下标）
- 维度字段改用 `getattr(row, dimension, None)` 通过 labeled 列名取值
- 防御性加上 `getattr(comp, "weight", 0)` 兜底空值
- 兼容 SQLAlchemy 2.x 的 `Row` / `RowMapping` 行为差异

### 13. 投资复盘 - 成分股按 sold/holding 状态拆行展示

**解决方案：** 原投资复盘每个手办只展示一行，无法应对「同一手办买入多体，部分在柜、部分已出」的真实场景（如「桐宫美月 写实版」买入 3 体，1 体已出、2 体在柜）。参考 `hpi_redesign_v2.html` 投资复盘设计，将同一手办按状态拆分为 2 行展示（● 在柜·2体 / ● 已出·1体），让用户能清晰看到每个状态分片的收益、权重、贡献。

**实现逻辑：**

- **后端 `hpi_service.py`（企业级服务层）**：
  - `_get_sold_figure_map` 升级：返回 `{sell_price: 加权平均卖出价, sold_qty: 累计卖出体数}`，支持多笔卖出记录按体数加权
  - `_calculate_hpi` 重构：每只手办先计算「单体均价 unit_cost = 总买入金额 / 总买入体数」，再按 `sold_qty` / `holding_qty` 拆分为 0~2 行
    - 已出行：成本 = `unit_cost × sold_qty`，收益率 = `(sell_price - unit_cost) / unit_cost`
    - 在柜行：成本 = `unit_cost × holding_qty`，收益率 = `(current_price - unit_cost) / unit_cost`
  - 成本基准统一为「单体均价」，避免多笔不同价格买入时分片成本不一致
  - HPI 公式恒等：`Σ(权重) = 1`，`HPI = 1000 × (1 + Σ(权重×收益率)/100)` 保持不变
  - `total_figures / holding_figures / sold_figures` 改为「体数总和」而非「行数」，与设计稿「累计交易 N 体」语义一致
- **后端 `_get_today_components` / `get_components`**：天然支持返回多行（每行带 `is_sold` 区分），前端 `v-for` 直接渲染
- **后端 `_calculate_and_save`**：delete 逻辑不变（按 user_id + record_date 删全部），insert 循环天然支持多行
- **前端 `InvestmentReview.vue`（组件目录）**：
  - `v-for` key 改为 `${figure_id}-${is_sold ? 'sold' : 'holding'}` 避免重复 key
  - 状态徽标在 `quantity > 1` 时追加「· N体」后缀（如「● 在柜 · 2体」）
  - meta 文本根据 quantity 分支：单行显示「买入 ¥X → 现价 ¥Y」；多体显示「买入 ¥X/体 → 现价 ¥Y · 在柜 N体」
  - 卖出统计按「体」加权：`soldUp / soldDown / soldTotal` 使用 `c.quantity` 累加，确保投资胜率分母为「总卖出体数」
- 「累计交易金额」按行求和（拆行后总和不变，结果一致）

### 16. 修复投资复盘与持仓列表成本价不一致缺陷

**解决方案：** 排查发现「行情-投资复盘」用「总金额 / 订单数」简单均价计算成本，而「资产-持仓列表」用 FIFO 剩余持仓成本计算成本，两种口径并存导致同一手办在两个模块显示的成本价对不上（例如桐宫美月 写实版：投资复盘 ¥919 vs 持仓列表 ¥800）。将 HPI 口径改为「在柜取 `HoldingPositionService` 的 FIFO 剩余成本 / 已出取 `AssetTransaction.sell` 记录的 FIFO 出库成本」，与持仓列表完全一致。

**实现逻辑：**

- **后端 `hpi_service.py`（企业级服务层）**：
  - 新增 `from app.models.asset import AssetTransaction` 导入
  - `_calculate_hpi` 阶段新增「FIFO 预计算」：对每个手办分别计算在柜 FIFO 成本与已出 FIFO 成本，并累加为总成本 `total_amount`，保证权重分母与每行 `buy_amt` 严格一致
  - 在柜行成本 = `HoldingPositionService.calculate_remaining_cost_price(db, figure_id, user_id)`（与资产-持仓列表同源）
  - 已出行成本 = `Σ(sell_transaction.price × quantity) / Σ(quantity)`（FIFO 出库成本，来源于交易流水）
  - 每行的 `first_buy_price`、`buy_amt`、走势图贡献、权重全部使用对应口径的 FIFO 成本
- **数据校验**：跑批后桐宫美月 在柜行 buy=¥800（与持仓列表一致），已出行 buy=¥1300（FIFO 卖出的那笔原价），HPI=1500.0
- **无需迁移数据**：FIFO 成本由 Order + AssetTransaction + SoldOrder 即时计算，旧快照被新跑批覆盖

- **docker-compose.yml**：db 服务 volumes 挂载 `./docker/mysql/my.cnf:/etc/mysql/conf.d/my.cnf:ro`，容器启动时自动加载自定义配置

**验证：** `curl http://localhost:28620/api/figures/?skip=0&limit=15` 返回 HTTP 200，items 数量正确，wishlist 数据已过滤（仅 3 条正常手办记录）

### 32. 愿望清单 HPOI 六层防护抓取引擎

**解决方案：** URL 智能抓取原来仅使用模拟数据返回固定模板，无法真实解析 HPOI 页面。新增六层防护抓取机制，核心思路为"模拟真人行为 + 分散请求来源 + Cloudflare 绕过 + 本地缓存兜底"，将封禁概率降至接近零。

**实现逻辑：**

- **第一层：HTTP 请求引擎 (`browser_engine.py`)**：使用 `cloudscraper` 代替普通 requests。cloudscraper 可自动绕过 Cloudflare 挑战，携带完整浏览器请求头（User-Agent、Referer、Sec-Fetch-* 等）和 Cookie/Session，每次请求随机延迟 0.5-1.5 秒模拟人类操作
- **第二层：智能代理池 (`proxy_pool.py`)**：从环境变量 `HPOI_PROXY_LIST` 读取代理列表（逗号分隔），每次请求随机选取一个出口 IP。无可用代理时自动降级为直连。支持阿布云/快代理/站大爷/Bright Data 等代理服务商
- **第三层：令牌桶限流器 (`rate_limiter.py`)**：全局单例，默认每 20 秒 1 个请求，最多突发 2 个。请求需获取令牌，令牌耗尽时阻塞等待，避免触发 WAF 频率限制
- **第四层：MySQL 多级缓存 (`cache_manager.py` + `HpoiScrapeCache` 模型)**：新建 `hpoi_scrape_cache` 表，URL 的 SHA256 哈希作为唯一 Key，缓存原始 HTML + 解析后 JSON，有效期 30 天。同一 URL 只抓一次，后续请求直接返回缓存数据
- **第五层：HPOI 页面解析器 (`html_parser.py`)**：使用 BeautifulSoup 从 HTML 中提取手办名称、图片、定价、发售日期、厂商、比例、作品、材质等信息。支持 HPOI 页面结构的多种选择器，提取失败时自动降级
- **第六层：异常处理与降级 (`scraper_service.py`)**：整合所有层的编排入口。优先尝试代理抓取 → 失败后直连降级 → HTML 解析失败时回退为 ID 占位数据。所有异常均被捕获并记录日志，永不崩溃
- **后端 `wishlist_url_fetch_service.py`**：HPOI 链接走六层引擎，其他站点（Amiami/MFC）保留模板模拟。API 端点传入数据库会话以支持缓存读写
- **前端 `useWishlistUrlFetch.js`**：新增 `fetching`/`progressText`/`error` 状态，支持缓存命中提示和降级警告
- **前端 `WishlistUrlModal.vue`**：新增错误提示区块（红色背景），抓取中显示进度文本
- **后端 Dockerfile**：将 `demisto/python3:3.11.9.103842` 作为基础镜像（Alpine），无需额外系统依赖。通过 `pip install cloudscraper` 实现浏览器模拟能力
