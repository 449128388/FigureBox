### 3. 修复 hpoi_scrape_cache 表每次部署清空数据导致调试查不到缓存

**解决方案：** 每次 `docker-compose up -d --build` 部署时，迁移脚本执行 `HpoiScrapeCache.__table__.drop(engine)` + `Base.metadata.create_all(engine)`，导致 `hpoi_scrape_cache` 表中所有历史缓存数据被清空。调试页面因此查不到缓存记录。将迁移改为幂等模式，仅在表结构变化时执行 ALTER，不再 DROP 数据。

**实现逻辑：**

- **后端 `20260706_add_hpoi_scrape_cache.py`**：
  - 首次运行：`CREATE TABLE IF NOT EXISTS`（通过 `Base.metadata.create_all`）
  - 升级运行：检查 `raw_html` 列类型，若为 TEXT 则执行 `ALTER TABLE MODIFY blob`，否则跳过
  - 任何情况下不执行 DROP TABLE，已有数据始终保留

**注意：** 本次部署后数据库为空（因之前的 DROP 逻辑清空了数据），使用调试页面前请先执行一次「URL 智能抓取」重新填充缓存。未来部署缓存数据不再丢失。

### 6. 修复 URL 智能抓取解析数据错误（基于 JSON-LD 重写解析器）

**解决方案：** 旧解析器使用文本启发式匹配（CSS 选择器为空），提取的 name/manufacturer/price/release_date 等字段完全错误。HPOI 的 HTML 中嵌入了完整的 JSON-LD 结构化数据（schema.org/Product），直接从中提取各字段，将准确率从 ~40% 提升至 ~99%。

**实现逻辑：**

- **后端 `html_parser.py`** — 全部重写，按优先级三层降级：
  - **第一层（JSON-LD）**：正则提取 `<script type="application/ld+json">` 中的 `mainEntity` 块
    - `name` → `mainEntity.name`
    - `japanese_name` → `mainEntity.alternateName`（数组取首项）
    - `manufacturer` → description 中 `发行: ` 后的值
    - `work` → description 中 `原画: ` 后的值
    - `release_date` → description 中 `出货日: ` 后的值（中文日期转为 YYYY-MM）
    - `scale` → description 中 `比例: ` 后的值
    - `material` → description 中 `材质: ` 后的值
    - `price/currency` → description 中 `定价: ` 后的值，优先匹配人民币 `xxx元`，无则取日元 `xxx日元`
    - `image` → `mainEntity.image`
    - **关键技巧**：description 字段使用专用正则而非 `,` 分割提取，避免数字内的逗号（如 `33,000`）导致字段断裂
  - **第二层（meta tags）**：无 JSON-LD 时使用 `og:title`/`og:image`/`twitter:image`
  - **第三层（文本启发式）**：使用关键词 + 正则全页搜索

### 7. 修复缓存命中时返回旧解析器数据，新解析器不生效

**解决方案：** 重写解析器后用户抓取同一 URL 仍看到错误数据。原因是缓存命中（`CacheManager.get()`）直接返回了 `record.parsed_data`（旧解析器存入的错误数据），新解析器从未被执行。修改为：缓存命中时取 `raw_html` 用当前解析器重新解析并更新缓存。

**实现逻辑：**

- **后端 `cache_manager.py`**：`get()` 返回字典新增 `raw_html` 字段，从数据库读取 gzip 压缩的原始 HTML 解压后返回
- **后端 `scraper_service.py`**：缓存命中后，先尝试用 `HpoiParser.parse(raw_html)` 重新解析，成功则 `CacheManager.set()` 覆盖旧 `parsed_data`，返回新版数据。失败时降级返回旧数据

**使用方式：** 无需任何额外操作，再次点击「URL 智能抓取」即可自动用新解析器覆盖缓存数据

### 13. 修复 MySQL sort_buffer_size 不足导致 /api/figures/ 500 错误

**解决方案：** `GET /api/figures/` 执行 `ORDER BY figures.id DESC` 时，MySQL 的 `sort_buffer_size` 仅 256KB（默认值），在有一定数据量的情况下触发 `Out of sort memory (1038)` 错误。Windows 挂载的 `my.cnf` 因文件权限问题被 MySQL 忽略，配置未生效。

**实现逻辑：**

- **`docker-compose.yml`**：在 `db` 服务中增加 `command: --sort-buffer-size=8388608`（8MB），该参数通过 MySQL Docker entrypoint 正确传递给 `mysqld`，绕过 Windows 挂载文件的权限问题
- **`docker/mysql/my.cnf`**：配置值从 4MB 提升至 8MB，增加注释说明权限问题，提示应通过 `--sort-buffer-size` 命令行参数传递

### 18. 修复解析结果中材质(material)字段含英文逗号时返回 null

**解决方案：** 愿望清单搜索栏使用原生 `<input>` / `<select>` 控件，样式简陋与手办管理模块（使用 Element Plus）不一致，且月份级 `type="month"` 控件在不同浏览器表现差异较大。

**实现逻辑：**

- **前端 `WishlistFilterBar.vue`**：将原生的输入框/下拉/月份控件替换为 Element Plus 组件：`el-input`（名称）、`el-select`（状态、厂商）、`el-date-picker type="daterange"`（预计发售区间）。日期范围通过 `value-format="YYYY-MM-DD"` 直接产出标准日期字符串，免去原月精度拼接逻辑。
- **前端 `useWishlist.js`**：`filterStart` / `filterEnd` 由 YYYY-MM 月精度改为 YYYY-MM-DD 日精度；`loadList()` 中直接透传 `release_start` / `release_end`，移除原月转日的拼接代码。

### 28. 修复手办详情 API 返回 500 错误（材质含中文顿号）

**解决方案：** 后端 Pydantic schema `FigureBase` 对 `material` 字段进行字符白名单校验，`ALLOWED_CHARS_PATTERN` 允许的符号不含中文顿号 `、`（U+3001）。从 HPOI 抓取的材质数据（如 `ABS、PVC`）中的顿号触发校验失败，导致序列化响应时报 500。

**实现逻辑：**

- **后端 `schemas/figure.py`**：在 `ALLOWED_CHARS_PATTERN` 中新增 `\u3001`（中文顿号 `、`），使材质字段中的顿号通过字符校验。
