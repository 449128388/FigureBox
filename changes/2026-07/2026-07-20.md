## 缺陷修复

### 1. 修复本命厂商列表点击搜索按钮未触发接口请求的缺陷

**解决方案：** `Dashboard.vue` 在 `setup()` 中从 `useManufacturer` 组合式函数解构出的 `handleSearch` / `handleFilterChange` / `handleResetSearch` / `searchKeyword` / `filterType` 等新增变量未写入 `return` 语句暴露给模板，导致 `@search` / `@filter-change` / `@reset` 事件处理器为 `undefined`、`:keyword` / `:filter-type` 透传 prop 始终为空字符串，点击搜索按钮无任何 API 请求。

**实现逻辑：**

- **前端** `Dashboard.vue` 的 `setup()` return：补齐 `handleManufacturerSearch` / `handleManufacturerFilterChange` / `handleManufacturerResetSearch` 三个事件处理器和 `manufacturerKeyword` / `manufacturerFilterType` 两个透传 prop，使模板能正确解析事件回调与 prop 绑定
- 修复后点击搜索 / 筛选 / 重置按钮均能正确触发 `/collector/manufacturers?keyword=xxx&filter_type=yyy` 请求

### 2. 修复筛选标签计数随当前筛选状态变化而非全局统计的缺陷

**解决方案：** 「全部 / 有在柜 / 无在柜」三个标签的数字应反映**全量**（仅受 keyword 影响）数据，而非当前 filter_type 过滤后的列表。原实现在前端基于已过滤的 `manufacturers` 数组聚合，导致点击「有在柜」后 `manufacturers` 只剩 6 条，「全部 6 / 有在柜 6 / 无在柜 0」全部错位。改为后端独立计算与 filter_type 解耦的统计字段返回给前端。

**实现逻辑：**

- **后端** `collector_manufacturer_service.py` 的 `get_all`：将返回值由 `list` 改为 `dict`，新增 `stats = {all, in, out}` 字段，统计遍历时累加而不受后续 `filter_type` 过滤影响（仅受 keyword 影响）
- **后端** `manufacturers.py` 的 `GET /collector/manufacturers`：直接透传 Service 返回的 `dict`（含 `manufacturers` / `total` / `stats`），保持接口契约兼容
- **前端** `composables/useManufacturer.js`：新增 `manufacturerStats` ref；`fetchManufacturers` 成功时写入 `response.stats`，失败时保底置零
- **前端** `ManufacturerList.vue`：新增 `manufacturerStats` prop；将 `totalAll` / `totalIn` / `totalOut` 三个 computed 改为直接读取 `manufacturerStats.{all,in,out}`，不再依赖已过滤的 `manufacturers` 数组
- **前端** `Dashboard.vue`：在 `setup()` 解构与 return 中补齐 `manufacturerStats` 并通过 `:manufacturer-stats` 透传给子组件
- 修复后无论选中「全部 / 有在柜 / 无在柜」，三个标签数字均稳定显示「全部 10 / 有在柜 6 / 无在柜 4」

### 3. 修复本命厂商详情页编辑保存后数据未实时刷新的缺陷

**解决方案：** `useManufacturer` 组合式函数的 `saveManufacturer` 在保存成功后只调用了 `fetchManufacturers()` 刷新列表，未判断当前是否在详情页，导致用户在详情页编辑保存后，`currentManufacturer` 仍指向旧数据，详情页 Hero 区域名称 / 描述 / Logo 全部未更新。

**实现逻辑：**

- **前端** `composables/useManufacturer.js` 的 `saveManufacturer`：在 `fetchManufacturers()` 之后增加判断 `currentView === 'detail' && currentManufacturer?.id === editingId`，命中则调用 `fetchManufacturerDetail(editingId)` 重新拉取该厂商详情，使 Hero 区域、统计、关联手办列表均实时反映编辑后的数据
- 仅当编辑的是当前详情页显示的厂商时才刷新，避免编辑其他厂商时无谓请求

### 4. 本命厂商详情新增「愿望中」状态筛选

**解决方案：** 收藏家模式 - 本命厂商详情页之前只展示「全部 / 在柜 / 预定中 / 已出」四种状态，遗漏了收藏家自己的愿望清单手办（`figures.purchase_type == 'wishlist'`）。这些手办与本命厂商存在强关联（同一品牌追厂轨迹），但无法在详情页集中查看。新增「愿望中」筛选 tab + 橙色徽章，让收藏家一目了然地查看本厂下尚未入手的愿望单手办。

**实现逻辑：**

- **后端** `collector_manufacturer_service.py` 的 `_get_figures_by_manufacturer`：在状态判定最前置追加「`fig.purchase_type == 'wishlist'` → `statuses.append('wish')`」分支；其他状态判定保持不变，愿望中手办若已购买仍可同时获得 `in` 状态
- **后端** `collector_manufacturer_service.py` 的 `_get_figure_stats`：新增 `wish_count` 统计，统计 `matched_ids` 中 `purchase_type == 'wishlist'` 的手办数
- **后端** `collector_manufacturer_service.py` 的 `get_by_id`：响应体中透出 `wish_count` 字段
- **前端** `ManufacturerDetail.vue`：`filterTabs` 在「已出」之前插入 `{ key: 'wish', label: '愿望中' }`；`filteredFigures` 新增 `wish` 分支过滤 `statuses.includes('wish')` 的手办；`statusClass` / `statusText` 新增 `wish` → `st-wish` / 「愿望中」映射；CSS 新增 `.st-wish { background: #FF9F43; }` 橙色徽章
- 修复后当手办 `purchase_type == 'wishlist'` 时，手办卡片左上角显示橙色「愿望中」徽章，点击「愿望中」tab 可只筛选该类手办

### 10. 本命厂商列表按总藏品数+在柜数双键排序

**解决方案：** 本命厂商列表默认按 `sort_order` + `created_at` 排序，排序字段与手办统计无关，用户关注的「总藏品」「在柜」两个核心数据无法直接驱动列表顺序。本调整让用户更重视的收藏热度优先展示。

**实现逻辑：**

- **后端** `collector_manufacturer_service.py` 的 `get_all`：
  - 将单次循环拆分为「先聚合统计 → 排序 → 再应用 filter」两阶段
  - 第一遍遍历：为每个厂商计算 `_get_figure_stats` 得到 `total_count` / `in_count`，与 `manufacturer` 对象一起存入 `items` 列表
  - 第二步：用 Python `list.sort(key=lambda x: (total_count, in_count), reverse=True)` 对 `items` 进行双键降序排序，总藏品数相同时按在柜数降序
  - 第三遍遍历：依次应用 `filter_type` 过滤 + 构造返回 dict
  - `stats` 全局统计（all/in/out）仍基于全部命中关键词的厂商，与排序解耦不受影响
