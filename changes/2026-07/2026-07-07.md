### 1. 第一层引擎替换为 Playwright（真实浏览器级模拟）

**解决方案：** 原 HPOI 抓取引擎使用 cloudscraper + requests（纯 HTTP 请求），无法执行 JavaScript 渲染，HPOI（Vue SPA）的商品数据无法获取；且 TLS 指纹为 Python 特征，易被 WAF 识别。将第 1 层引擎替换为 Playwright + Chromium 真实浏览器，彻底解决 JS 渲染和 TLS 指纹两个核心问题。

**实现逻辑：**

- **后端 `browser_engine.py`**：
  - 使用 `playwright.sync_api` 启动 headless Chromium，完整执行 JavaScript 渲染（HPOI 的 Vue SPA 数据可正常获取）
  - 携带真实 Chrome 126 的 TLS 指纹（与 Python urllib3 的指纹完全不同，无法从 TCP 握手阶段识别）
  - 注入反检测脚本：隐藏 `navigator.webdriver`、伪造 `navigator.plugins`、覆盖 `permissions.query` API，消除 Playwright 自动化标记
  - 模拟人类行为：networkidle 等待 → 随机停留 2-5 秒 → 模拟滚动到底部 → 再停留 0.5-1 秒，行为模式与真实用户一致
- **后端 `Dockerfile`**：
  - 基础镜像从 `demisto/python3:3.11.9.103842`（Alpine/musl）改为 `python:3.11-slim-bookworm`（Debian 12/glibc），glibc 对 Playwright 和各类 Python 包兼容性更好
  - 安装 Playwright 系统依赖（libnss3/atk/cups/libdrm 等）+ `pip install playwright` + `playwright install chromium` 自动下载 Chromium 149
  - 通过 `playwright install-deps chromium` 自动安装 Xvfb、字体、Mesa 等可选依赖，节省手动管理
- **后端 `requirements.txt`**：新增 `requests`（slim-bookworm 不自带，用于 exchange_rate_service）

### 2. 反检测增强：UA 池/持久化浏览器/视口随机化/指纹随机化

**解决方案：** 上一版引擎存在 4 个易被 WAF 识别的自动化特征——单 User-Agent、每次请求新建浏览器、固定 1920×1080 视口、无浏览器指纹随机化。逐一增强使浏览器行为与真实用户无法区分。

**实现逻辑：**

- **后端 `browser_engine.py`**：
  - **UA 池随机切换**：定义 10 个 User-Agent（Chrome 121~130，Windows 和 macOS 混用），每次创建 context 时 `random.choice` 选择，WAF 聚合分析无法关联
  - **持久化 browser 实例**：BrowserEngine 改为进程级单例，首次调用 `launch` 后保持 browser/context 不关闭。所有请求复用同一实例，Cookie/localStorage 累积形成真实历史会话。代理变更（`_current_proxy` 变化）时自动重建
  - **视口随机化**：预定义 9 个分辨率（1366×768 到 2560×1440），每次创建 context 时随机选取
  - **Canvas 指纹随机化**：重写 `fillText` 和 `getImageData`，对每个像素坐标和 RGBA 值施加 ±1 的随机扰动，每次渲染产生独一无二的 Canvas 指纹
  - **WebGL 指纹随机化**：拦截 `getParameter(37445/37446)`（UNMASKED_VENDOR/RENDERER），返回固定值 `Intel Inc.` / `Intel Iris OpenGL Engine`，隐藏真实 GPU 信息
  - **AudioContext 指纹随机化**：拦截 `getFrequencyData`，对频域数据施加 ±1 随机扰动

### 3. 修复 hpoi_scrape_cache 缓存写入失败 + 解析器改进

**解决方案：** 从链接添加愿望时提示"抓取成功"，但 `hpoi_scrape_cache` 表中缺乏对应缓存数据。两个原因：① Playwright 渲染后的 HTML 约 121KB，超过 MySQL `Text` 类型的 65KB 限制，`raw_html` 写入失败；② HPOI 解析器的 CSS 选择器为空数组 `[]`，全靠文本启发式匹配，提取的 `name`/`manufacturer`/`price`/`release_date` 等字段不正确。

**实现逻辑：**

- **后端 `cache_manager.py` + `hpoi_cache.py`**：
  - `raw_html` 存储前使用 `gzip.compress` 压缩（121KB → ~15KB），MySQL `LargeBinary` 字段无大小限制
  - 读取时自动 `gzip.decompress` 还原（为后续调试保留完整 HTML）
  - 更新 `hpoi_cache.py` 模型：`raw_html` 列类型从 `Text` 改为 `LargeBinary`
  - 迁移脚本增加 `DROP TABLE IF EXISTS` 逻辑，启动时重建表结构
- **后端 `html_parser.py`**：
  - 名称提取优先级：`meta[property=og:title]` → `<title>`（自动去站点后缀） → `<h1>`
  - 封面图提取：`meta[property=og:image]` → `meta[name=twitter:image]` → `img[src~=hpoi.net/gc]`
  - 厂商/比例/作品/材质、发售日期、定价均使用改进的关键词匹配 + 正则模式提取

### 4. 新增 raw_html 调试模块

**解决方案：** 需要一种直观的方式验证抓取引擎是否正常工作、缓存是否写入成功、解析后的数据是否准确。新增独立调试页面，输入 URL 即可查看缓存中的原始 HTML 和解析数据，方便排查解析器问题。

**实现逻辑：**

- **后端 `wishlist_url_debug.py`**：新增 `GET /api/wishlist/debug/raw-html?url=xxx` 端点，从 `hpoi_scrape_cache` 表中按 URL 哈希查找记录，自动 gzip 解压返回完整 HTML、解析数据和缓存有效期
- **前端 `WishlistDebug.vue`**：独立调试页面，URL 输入框 + 查看按钮，分两个区块展示解析数据（JSON 格式化）和原始 HTML（深色代码高亮 + 大小标注 + 一键复制）
- **前端 `WishlistHeader.vue`**：刷新按钮旁新增 `ri-bug-line` 调试入口图标按钮，hover 变紫色
