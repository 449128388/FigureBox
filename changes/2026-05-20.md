### 已出售订单快速卖出修改场景优化

#### 需求描述
针对已出售订单中快速卖出的订单，区分两种修改场景，分别处理交易记录：

**场景 1：仅修改纯信息字段**
- 涉及字段：卖出平台、订单编号、卖出状态、买家手机号、买家地址、快递单号、发货日期、备注
- 处理方式：`order_transactions` 和 `asset_transactions` 两张表都不变更

**场景 2：修改金额相关字段**
- 涉及字段：卖出价、运费、手续费
- 处理方式：仅 `order_transactions` 变更

#### 解决方案
1. **场景区分逻辑**：
   - 在 `update_sold_order` 方法中判断修改的字段类型
   - 纯信息字段修改：只更新 `sold_orders` 表
   - 金额字段修改：额外更新 `order_transactions` 记录

2. **新增更新方法**：
   - 在 `SoldOrderTransactionService` 中添加 `update_sold_order_transactions` 方法
   - 根据 `sold_order_id` 查询关联的 `order_transactions` 记录
   - 更新卖出收入、运费支出、手续费支出三条记录

3. **边界处理**：
   - 运费/手续费从有到无：软删除对应记录
   - 运费/手续费从无到有：创建新记录
   - 币种转换：使用 `CurrencyService` 统一转换为人民币

#### 实现逻辑
| 修改项 | 影响表 | 处理方式 |
|--------|--------|----------|
| 卖出平台、订单编号、状态等纯信息字段 | `sold_orders` | 仅更新本表 |
| 卖出价 | `order_transactions` | 更新 sell 类型记录的 amount 字段 |
| 运费 | `order_transactions` | 更新/创建/删除 fee 类型记录（changed_field='shipping_fee'） |
| 手续费 | `order_transactions` | 更新/创建/删除 fee 类型记录（changed_field='platform_fee'） |

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_transaction_service.py`: 新增 `update_sold_order_transactions` 方法
- `backend/app/services/sold_order_service/sold_order_crud_service.py`: 在 `update_sold_order` 中调用更新方法

#### 结果
- 纯信息字段修改不再影响交易记录，保持历史数据完整性
- 金额字段修改自动同步到资金流水，确保财务数据准确性

### 已出售订单卖出数量变更处理

#### 需求描述
当修改已出售订单的卖出数量时，联动更新库存账（asset_transactions）和资金账（order_transactions）。

**场景A：数量减少（如 2体 → 1体）**
- 回库数 = 原数量 − 新数量
- asset_transactions：插入 RETURN 记录，恢复库存
- order_transactions：UPDATE 数量字段

**场景B：数量增加（扣库）**
- 增扣数 = 新数量 − 原数量
- 库存校验：检查当前库存是否足够
- asset_transactions：插入 SELL 记录，扣减库存
- order_transactions：UPDATE 数量字段

#### 解决方案
1. **实时加权平均成本计算**：
   - 新增 `calculate_average_cost` 方法
   - 基于当前买入记录的 remaining_quantity 计算加权平均成本

2. **数量变更处理服务**：
   - 新增 `update_quantity_on_sold_order_change` 方法
   - 区分场景A（回库）和场景B（扣库）
   - 场景A使用原订单成本价，场景B使用实时加权平均成本

3. **资金流水数量更新**：
   - 新增 `update_sell_transaction_quantity` 方法
   - 更新 order_transactions 中的 quantity 和 amount 字段

4. **库存校验与处理**：
   - 数量增加时先校验库存
   - 库存不足时回滚事务并返回错误

#### 实现逻辑
| 场景 | 数量变化 | asset_transactions | order_transactions | 成本计算方式 |
|------|----------|-------------------|-------------------|-------------|
| 场景A | 减少 | 插入 RETURN 记录 | UPDATE 数量 | 原订单成本价 |
| 场景B | 增加 | 插入 SELL 记录 | UPDATE 数量 | 实时加权平均成本 |

**关键细节**：
- 数量增加时，新扣减部分的成本价必须按当前实时加权平均成本计算
- 第一次卖出后，如果又买了低价散货，整体成本会被摊薄或拉高

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_inventory_service.py`: 新增数量变更处理和成本计算方法
- `backend/app/services/sold_order_service/sold_order_transaction_service.py`: 新增资金流水数量更新方法
- `backend/app/services/sold_order_service/sold_order_crud_service.py`: 在 update_sold_order 中调用数量变更处理

#### 结果
- 卖出数量变更时自动同步更新库存账和资金账
- 数量增加时进行库存校验，防止超卖
- 成本计算准确反映实时库存成本

### 优化已出售订单数量减少时的 FIFO 赎回退回原则

#### 问题描述
当已出售订单数量减少（如 2体 → 1体）时，需要实现正确的 FIFO 赎回退回原则：
- **卖出时**：先进先出（FIFO）- 先买入的先卖出
- **赎回时**：后进先出（LIFO）- 后卖出的先退回

之前的实现只是简单地按买入时间倒序恢复买入记录，没有遵循"后卖先回"的原则。

#### 问题原因
1. 卖出时记录了从哪些买入记录扣减（按 FIFO 顺序）
2. 但赎回时没有按扣减记录的倒序恢复，而是简单地按买入时间倒序恢复

#### 解决方案
1. 从卖出记录的 notes 中解析扣减记录信息
2. 按扣减记录的**倒序**恢复买入记录（后卖先回）
3. 如果还有未恢复的数量（旧数据兼容），再按买入时间倒序恢复

**实现逻辑**：
- 卖出时：先扣减 record[0]，再扣减 record[1]...
- 赎回时：先恢复 record[-1]，再恢复 record[-2]...

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_inventory_service.py`: 修改 `update_quantity_on_sold_order_change` 方法中的场景A逻辑，实现 FIFO 赎回退回原则

#### 结果
- 数量减少时，后卖出的物品优先退回库存
- 持仓成本价恢复符合 FIFO 赎回退回原则
- 库存账（asset_transactions）记录更准确

### 优化已出售订单 order_transactions 的 unit_price 计算逻辑

#### 问题描述
在已出售订单模块创建 order_transactions 数据时，`unit_price` 应该定义为**净单价**（每体实际到账金额），而不是原始的卖出单价。

#### 计算公式
```
unit_price = (卖出单价 × 数量 − 运费 − 手续费) / 数量
```

#### 问题原因
之前的实现直接使用卖出价格作为 unit_price，没有扣除运费和手续费，不能反映每体的实际到账金额。

#### 解决方案
修改 `create_sell_order_transaction` 和 `update_sold_order_transactions` 方法：
1. 计算总卖出金额（卖出单价 × 数量）
2. 扣除运费和手续费（转换为人民币）
3. 计算净单价：净金额 / 数量
4. 同时更新 quantity 字段为实际卖出数量

#### 涉及文件
- `backend/app/services/sold_order_service/sold_order_transaction_service.py`: 修改 sell 类型交易的 unit_price 和 total_amount 计算逻辑

#### 结果
- order_transactions 中的 unit_price 反映每体的实际到账金额
- total_amount 反映订单的实际净收入
- 资金流水数据更准确，便于财务统计

添加已出售订单时，成本价计算与持仓列表（按盈亏排序）中的成本价不一致：
- **已出售订单**：使用 `figure.average_purchase_price`，从订单计算平均入手价
- **持仓列表**：使用 `calculate_remaining_cost_price`，从库存账计算实际剩余持仓成本
- 卖出后，库存账的成本会重新计算（基于剩余数量），而订单账的平均价格不会变，导致两者不一致

#### 解决方案
1. **后端**：创建手办成本查询服务，与持仓列表使用相同的计算逻辑
   - 创建 `FigureCostService` 服务类，提供 `get_figure_cost_price` 方法
   - 从 `AssetTransaction` 库存账计算实际剩余持仓成本
   - 创建 API 端点 `GET /api/assets/figures/{figure_id}/cost`

2. **前端**：创建业务逻辑 composable，分离UI层与业务逻辑
   - 创建 `useFigureCost.js` composable，封装成本价获取逻辑
   - 更新 `BasicInfoTab.vue` 组件，调用 API 获取成本价

#### 实现逻辑
- 选择手办时，前端调用 `/api/assets/figures/{figure_id}/cost` API
- 后端使用 `HoldingPositionService.calculate_remaining_cost_price` 计算成本
- 计算逻辑与持仓列表完全一致，确保数据一致性
- 成本价自动填充到订单表单，用户无法手动修改

#### 涉及文件
- `backend/app/services/dashboard_service/assets_service/figure_cost_service.py`: 手办成本查询服务
- `backend/app/api/assets/operation_figure_cost.py`: 成本查询 API 端点
- `backend/app/api/assets/assets_router.py`: 注册成本查询路由
- `frontend/src/views/SoldOrders/composables/useFigureCost.js`: 成本价获取 composable
- `frontend/src/views/SoldOrders/components/form/BasicInfoTab.vue`: 更新成本价获取逻辑

#### 结果
- 已出售订单的成本价与持仓列表保持一致
- 卖出后成本价基于库存账重新计算，反映实际剩余持仓成本
- 采用前后端分离架构，业务逻辑与UI层分离

### 修复成本查询 API 401 认证错误

#### 问题描述
调用 `GET /api/assets/figures/{figure_id}/cost` API 时返回 401 Unauthorized 错误。

#### 问题原因
前端 `useFigureCost.js` 中直接使用了 `axios`，而不是使用配置好的 axios 实例（位于 `frontend/src/axios/index.js`）。配置好的 axios 实例包含请求拦截器，会自动添加 `Authorization` header 携带 token。

#### 解决方案
修改 `useFigureCost.js`，从 `axios` 改为导入配置好的 axios 实例 `../../../axios`。

#### 涉及文件
- `frontend/src/views/SoldOrders/composables/useFigureCost.js`: 修复 axios 导入路径

#### 结果
- API 请求正确携带 token，认证通过
- 成本价查询功能正常工作
