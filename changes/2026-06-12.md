# 2026-06-12 更新日志

## 1. 修复新增手办关联订单时资金流水记录不完整

### 问题背景
在手办管理页面新增关联订单时，只有状态为"已完成"的订单会记录资金流水和库存账，状态为"已支付"和"已取消"的订单缺少资金流水记录。

### 解决方案
根据订单状态分场景处理交易记录，确保资金流水完整、库存账准确。

### 实现逻辑
- **"已完成"订单**：同时记录资金流水（`order_transactions`，含定金+尾款）+ 资产交易库存账（`asset_transactions`），并更新手办平均入手价和持有数量
- **"已支付"订单**：只记录资金流水（`order_transactions`，含定金+尾款），表示有资金流出但货物未到，不操作库存账
- **"已取消"订单**：只记录资金流水（`order_transactions`，含定金+尾款），表示已产生过资金支付但订单已取消，不操作库存账
- **"未支付"订单**：不记录任何数据，保持原逻辑不变（无资金流动）

### 结果
- 已支付和已取消的新增订单在资金账中可追溯
- 库存账与手办实际库存保持一致
- 未支付订单仍然不产生任何记录

## 2. 修复编辑手办关联订单时资金流水记录不完整

### 问题背景
在手办管理页面编辑关联订单时，如果将订单从"未支付"改为"已支付"或"已取消"，由于之前未创建初始资金流水记录，编辑后仍然缺少资金流水记录。

### 解决方案
在订单编辑流程中增加初始记录创建检测，当订单状态变更为"已支付"、"已取消"或"已完成"且尚无资金流水记录时，自动创建初始记录。

### 实现逻辑
- **编辑为"已完成"**：检测若无初始资金流水记录则创建（含定金+尾款），若无资产交易记录则创建库存账，并更新手办平均入手价
- **编辑为"已支付"**：检测若无初始资金流水记录则创建（含定金+尾款），不操作库存账
- **编辑为"已取消"**：检测若无初始资金流水记录则创建（含定金+尾款），不操作库存账
- **编辑为"未支付"**：不记录任何数据，保持原逻辑不变

### 结果
- 从"未支付"编辑为"已支付"或"已取消"后，资金账可追溯
- 从"未支付"编辑为"已完成"后，库存账同步更新
- 编辑时不重复创建已有记录

## 3. 修复资产看板API 500错误（上证指数缓存updated_at为None）

### 问题背景
清空数据库后访问资产看板API时返回500 Internal Server Error，服务端日志显示 `TypeError: unsupported operand type(s) for -: 'datetime.datetime' and 'NoneType'`。

### 解决方案
在指数缓存检查逻辑中增加 `updated_at` 为 `None` 的空值判断。

### 实现逻辑
- **问题原因**：`_check_need_fetch` 方法中执行 `datetime.now() - cache.updated_at` 时，`cache.updated_at` 可能为 `None`，导致类型错误
- **修复点1（防御性）**：在减法计算前增加 `if cache.updated_at is None: return True`，当更新时间为空时直接判定需要重新获取数据
- **修复点2（根因）**：`_save_index_data` 创建新 `StockIndexCache` 记录时缺少 `updated_at` 字段赋值，导致新增记录该字段为 NULL。在新建记录时显式设置 `updated_at=now`

### 结果
- 资产看板API恢复正常访问
- 500错误已修复
- 缓存数据为空时自动触发重新获取

## 20. 修复API请求校验返回信息冗余

### 问题背景
调用 `/api/sold-orders/create-from-inventory` POST 接口时，当请求参数校验失败（如手机号格式错误），返回的错误信息包含 Pydantic 底层错误详情（如 "1 validation error for SoldOrderCreate" 和错误参考链接），而不仅仅是自定义的业务错误提示文字。

### 解决方案
添加自定义 `RequestValidationError` 异常处理器，拦截请求校验异常，仅提取业务错误信息返回。

### 实现逻辑
- **问题原因**：FastAPI 默认的 `RequestValidationError` 处理器会原样返回 Pydantic 验证错误的完整结构，包含模式名、字段名、错误类型和参考链接等技术细节
- **修复**：
  - 在 `main.py` 中注册 `@app.exception_handler(RequestValidationError)` 和 `@app.exception_handler(ValidationError)`
  - 从 `exc.errors()` 中提取每个错误的 `msg` 字段，去除 `"Value error, "` 前缀
  - 去重后拼接为简洁的错误信息字符串
  - 返回 `{"detail": "业务错误提示"}` 格式的简洁响应

- **补充修复**：
  - 在 `CreateFromInventoryRequest` 中添加 `buyer_phone` 字段校验器，使手机号格式校验在请求层即触发，避免在函数体内部构造 `SoldOrderCreate` 时才抛出错误
  - 补充 `ValidationError` 异常处理器，覆盖函数体内部构造 Pydantic 模型时抛出的校验异常

### 结果
- 校验失败时只返回业务错误提示（如 "手机号格式不正确，请输入11位有效手机号"）
- 不再显示 Pydantic 底层技术细节
- 所有 API 接口的请求校验错误响应格式统一简洁

## 28. 修复持仓列表卖出功能的展示编号生成

### 问题背景
资产看板-持仓列表卖出功能（以及快速操作卖出功能）中，`sold_orders` 表 `display_order_number` 数据格式错误，未正确生成 `SALE-YYYYMMDD-XXX` 格式的内部展示编号。

### 解决方案
在 `SoldOrderCrudService.create_sold_order()` 中显式设置 `created_at` 和 `updated_at`，同时在模型层添加客户端 `default` 确保时间戳立即可用，使 `update_display_number()` 能获取正确的时间戳生成编号。

### 实现逻辑
- **根因分析**：`created_at` 字段仅使用 `server_default=func.now()`（数据库端默认值），`flush()` 后 `created_at` 未加载到 Python 对象中，导致 `update_display_number()` 使用 `None` 时间戳生成 `SALE-{id}`（不含日期）
- **`sold_order_crud_service.py`**：在创建 `SoldOrder` 对象时显式传入 `created_at=datetime.now(), updated_at=datetime.now()`
- **`sold_order.py`（模型）**：为 `created_at` 和 `updated_at` 添加 `default=datetime.now` 客户端默认值，与其他代码路径保持一致

### 结果
- `display_order_number` 正确生成为 `SALE-YYYYMMDD-XXX` 格式
- `created_at` 和 `updated_at` 创建时即有值，不再依赖数据库回填
